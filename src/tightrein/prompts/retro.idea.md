# 要做的事

1. 读懂这个问题：出在哪一步、哪个调用点，现象是什么，每次出现的数据说明了什么。
2. 写一两句解决思路：先想它属于哪一类(时限、资源与用量、交接、恢复、边界、提示、配置的阈值)，按类给出通用的办法。
3. 判断值不值得沉淀为经验或规则：只有下次还用得上、能写成一条通用规则的才写，否则为 null。
4. 写完即停；不读代码、不搜索、不运行命令，只依据本次输入。

# 规则与边界

- 先通用兜底：能在协议层或配置中解决的，不建议在某个步骤里加特判；只是阈值或开关的问题，建议改 settings 中的取值，不改代码。
- 写下次还用得上的规律，不写这一次的经过；不出现人名、账号、数据值与凭证；材料不足就写「材料不足，先观察」，不硬凑。
- 不写「可能」「大概」「也许」，不写空话(如「优化性能」「加强检查」)，要说清改哪一类、改成什么样。
