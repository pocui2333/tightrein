# 去重(collect.dedup)

## 是什么

采集的最后一步(原「聚合」阶段)：每次采集运行结束时，就地把本次各来源交出的信号整理成问题，采集交出来的直接是问题，
评估只做判断。不调用模型。入口 `dedup(runtime, results) -> DedupOutcome`，由 `collect/collect.py` 调用。

## 流程

| 步骤 | 文件 | 做什么 |
|---|---|---|
| 规范化 | `normalize.py` | 去掉消息与位置中每次都变的部分；内置规则加项目规则 |
| 抑制 | `suppress.py` | 命中抑制规则(以前判为误报)的信号标记掉，不再往下走 |
| 归并 | `group.py`、`changes.py` | 算指纹；已有问题累计出现，同一处代码被别的来源报过的合进去，都没有则新建待确认的问题 |
| 复现确认 | `reproduce.py` | API 模糊测试的 5xx 重放确认；确定性来源直接有效；运行时偶发问题先观察 |
| 状态更新 | `status.py` | 再次出现累计；回归、已解决、观察期到次数、忽略到期的判定 |
| 输出 | `output.py` | 本次变成新发现或回归的问题各一份交给评估；运行交接；变更日志 |

`dedup.py` 按顺序执行各步：各步只改内存中的变更集(`ChangeSet`)，最后在一个事务里写入问题、出现、各来源的读取位置、
采集调度的上次时间、问题序列、关联 Issue 的重新打开与要落盘的文件清单。

### 规范化

内置规则按顺序：GUID → 带日期的时间 → 时刻 → 十六进制(必须同时含字母和数字，先于纯数字) → 4 位以上数字(短数字保留：
第 12 页、HTTP 404) → Windows 与 POSIX 路径 → 引号里的值；项目规则在内置规则之后；压缩空白；截到 200 字。
截断长度属于指纹算法的一部分，不做成可调项。

位置：接口为「方法 路由模板」(数字与 GUID 段换成 `{id}`)，页面为路由模板(换成 `:id`)，代码位置去掉末尾的 `:行[:列]`。
指纹、标题、覆盖判定都用规范化后的位置。

### 抑制

规则只能二选一：指纹，或来源加消息正则；到期日当天仍有效，次日起失效；第一条命中的生效。抑制在归并之前，指纹现算。
回归信号只能按消息匹配。规则两处来源：项目写的(`controls."collect.dedup".suppress`)在前；评估判为误报时
`SuppressionRule.for_fingerprint` 生成、`suppress.add` 存进 state 表的(到期日为当天加天数，不是永久抑制)在后。

### 指纹与归并

- 有 `group_key`(平台分组编号等)时原样作为指纹，便于回平台找同一组；
- 其余拼成带版本前缀的规范字符串 `v2|<来源>|<检查类型>|…`，取 SHA-1 前 16 位；不用行号：
  平台堆栈取异常类型加前 3 帧的符号(不含文件与行)，没有帧时取类别加规范化消息；接口取方法、路由模板、状态码大类
  (502 与 503 是同一个问题)；项目探针取探针名加探针给的指纹；静态巡检取规则加位置(带符号)；
- v2 比 v1 多了检查类型：同一处的不同问题(报错与变慢)不再并成一个；改算法时升版本，不与旧指纹混淆；
- 回归信号(证据带 `targetFingerprints`，验收时复现检查失败)不算指纹，直接归到原来的问题；找不到时写进说明，不新建；
- 跨来源合并：同一文件、同一函数(或行号相近，`nearbyLines`)、同属报错类或同属性能类，且是另一个来源报的，
  合成一个问题，指纹记为别名，证据都留着；人已下过结论的(closed、muted)不吸收；
- 按指纹找问题先看本次内存中的，再看从数据库批量读入的；同一次运行里同一指纹的第二条信号不会再建一个；
- 信号可能乱序到达：首次与最近出现按发生时间比较；信号没有 commit 时保留原值；每次出现把「干净的覆盖运行」清零；
- 信号按 (发生时间, 编号) 排序后处理，结果与来源交出的顺序无关。

### 复现确认

| 情况 | 结果 |
|---|---|
| `replayChecks` 中的来源与检查类型(缺省 API 模糊测试的 server_error)，且来源没标可复现 | 重放 `replayAttempts` 次：任一次复现 → new；有「无法判断」且没复现 → 保持 pending，下次重试；全部未复现 → intermittent |
| 来源没有重放器(`tightrein.<来源>.replay`) | 保持 pending |
| 确定性来源、已取证成立的信号 | new |
| 其余(运行时偶发) | 累计出现到 `watchOccurrences` 次 → new，否则 watching |

间歇与观察中的问题由状态更新处理：间歇的再次出现即转 new；观察中的在 `watchWindow` 内出现到 `watchOccurrences` 次转 new。

### 状态更新

- 状态转换只经 `status.TRANSITIONS` 查表，不在表中的组合抛 `TransitionRejected`，本次什么都不写；
- commit 的先后关系先汇总本次要用的 commit 对，一次查完(`Git.is_ancestor`)；查不到的视为未知，本次不做
  解决、回归、忽略到期判定，在说明中列出；
- 回归：已解决的问题只有出现在比「解决时 commit」严格更新的版本上(是祖先且不是同一个，兄弟分支不算)才算；
  旧版本上的迟到信号只累计；用本次出现中最晚一条带 commit 的信号判断；
- 已解决：来源运行覆盖了问题所在位置而问题没出现，并且运行对应的 commit 比问题最后出现的 commit 更新，才累计一次；
  到 `coveredRuns` 次(静态巡检 1 次，其余 3 次)判为已解决；
- 覆盖：只认 done 或 partial 的来源运行，按它实际读到、测到的范围(`SourceResult.coverage`)：
  同一来源；有子来源的看是否读到了该子来源；接口看问题涉及的每个角色都测到；代码看文件在扫描范围内；
  任务外发现的覆盖范围为空，永远不会因此判为已解决；被挡住、失败、跳过的运行不参与；
- 运行对应的 commit：`schedule.every` 为 `on_commit` 的来源取仓库 HEAD，其余取最近一次成功部署；
- 被忽略(muted)的恢复条件以忽略时的出现次数与最近 commit 为基准，任一满足即恢复为 new
  (到期日、再出现 N 次、出现在新版本、严重度升级——本次信号的严重度提示高于评估定的严重度)；都为空表示永久忽略；
- 判为误报算「判对」：评估判为不成立(已关闭)、结论还没有实际结果的问题，本次有指纹(含别名)相同的信号——包括被
  抑制规则挡掉的——即记为又出现过，不再算判对；没有且本次 done 或 partial 的同来源运行覆盖到它时累计一次，到
  `falsePositiveCleanRuns` 次把评估结论的实际结果(`problems.extra.assess.outcome`)回填为 `correct`，累计数记在
  `problems.extra.falsePositiveCheck`；重新评估(attempt 变了)后重新计数。被抑制的信号不关联到问题，所以按指纹查。

### 输出

- 交给评估的只是本次变成 new 或 regressed、到最后仍是这个状态且没有被合并的问题；有 Issue 的问题再次出现不重复送，
  回归的才送，并带上 Issue 编号；每个问题一份 `data/problems/<问题>/19-collect.dedup-handoff.json`；
- 样本按 (角色, 位置) 去重，从最近的取，最多 5 条，同一处的重复信号不占名额；
- 关联了 Issue 的问题回归时，按评估的 Issue 状态机(`assess/issue/transitions.py`)以 REOPEN 重新打开，与问题同事务写入；
  Issue 还在处理中(状态机不接受)时只在说明中记一笔；
- 运行交接 `data/runs/<运行>/19-collect.dedup-handoff.json`；变更日志 `19-collect.dedup-log.jsonl` 逐行记下
  本次写入的问题快照、出现与状态转换(连同上下文)；
- 中断恢复：要写的文件与问题在同一个事务里记进 state 表(`collect.dedup.unwritten`)，提交后再落盘、删掉记录；
  事务已提交、文件没写完就中断的，下次开始先补写。

## 输入与输出

- 输入：各来源的 `SourceResult`(信号、读取位置、覆盖范围)；数据库中的问题与出现；
- 输出：`DedupOutcome`(新发现与回归的问题编号、合并、抑制、解决、观察中的数目、量化数据)；problems、occurrences 表；
  上面列出的文件。
- 从文件重建：`output.rebuild_problems` 登记在 `store/rebuild.py`，按运行顺序重放各运行的变更日志，编号不变。

## 配置

`controls."collect.dedup"`(缺省在 `settings/defaults.json`，项目在工作区 `settings.json` 覆盖；列表用 `normalize+`、
`suppress+` 追加)：

| 键 | 含义 | 缺省 |
|---|---|---|
| `normalize` | 项目的规范化规则 `[{"pattern": 正则, "replacement": 替换}]`，在内置规则之后 | `[]` |
| `suppress` | 项目的抑制规则 `[{"match": {"fingerprint": …} 或 {"source": …, "messagePattern": …}, "reason", "addedOn", "expiresOn"}]` | `[]` |
| `watchWindow` | 偶发问题的观察期 | `24h` |
| `watchOccurrences` | 观察期内出现到几次送评估 | 2 |
| `coveredRuns` | 判为已解决所需的覆盖次数，按来源，`*` 为其余 | static 1，其余 3 |
| `nearbyLines` | 跨来源合并时「行号相近」的范围 | 10 |
| `titleLength` | 问题标题的长度上限 | 120 |
| `replayChecks` | 需要重放确认的「来源 → 检查类型」 | api_fuzz 的 server_error |
| `replayAttempts` | 每个问题重放几次 | 2 |
| `falsePositiveCleanRuns` | 判为不成立后被覆盖而未再出现几次即回填判对 | 3 |

## 设计依据

- 去重并入采集、就地成问题：合并后不再需要「哪些采集运行还没聚合」的记录与单独的全局锁(44 号计划 1.9)。
- 指纹不用行号、带版本前缀、加检查类型：代码一改行号就变，旧指纹对不上；版本前缀让算法升级不与旧数据混淆
  (旧 `domain/fingerprint.py`)。
- 先观察偶发问题、跨来源合并：在这里多挡一些，减少评估调用模型的次数(44 号计划 1.9「优化」)。
- 回归只在严格更新的 commit 上判定、未知不判：迟到信号与本地没同步的 commit 不会误判(旧 `domain/commit_facts.py`)。
- 一个事务写入、文件清单随事务保存：中断时数据库与文件不会一半新一半旧(旧 `pipeline/aggregate/changeset.py`、`service.py:recover`)。

## 不做什么

- 不调用模型，不判断问题是否成立、该不该修(那是评估的事)；
- 不改 Issue 正文(「历史」一节由评估的 Issue 模块维护)；
- 评估之后对问题的人工处理(关闭、忽略、关联 Issue)不写进去重的变更日志，由评估自己记录。
