# 交接文档(handoff)

## 是什么

每一步交出的东西(程序之间的 JSON、agent 的结构化输出、给人看的 Markdown)都按同一个顺序写四部分。程序在 `handoff.py`：`Handoff`、`Metrics`、`Tokens`、`Versions`、`Status`，必填事实的 schema 校验，读写 `handoff.json`。

## 怎么做

### 四部分

| 部分 | 写什么 | 谁来填 |
|---|---|---|
| 1 结论 | 状态(`passed`、`failed`、`pending`) + 一句话结论 | 程序(状态) + agent 或程序(一句话) |
| 2 必填事实 | 这一步规定必须交代的内容，字段固定，不能省略或写「见上文」 | 程序能得出的程序填；只有 agent 知道的 agent 填 |
| 3 量化数据 | 所有步骤共用的一组数字，全部由程序统计 | 程序 |
| 4 备注 | 推理、取舍、疑点；自由书写，最长 4000 字 | agent |

- 后面的步骤与下一次模型调用只拿前三部分(`Handoff.for_next_step`)，备注只给人看；不允许把必填事实只写在备注里；
- 必填事实按那一步的 schema(放在那一步的文件夹，2020-12)校验，错误带 JSON 路径与原因，一次列出全部(`FactsInvalid`)，缺了就要求重写；
- 每份 `handoff.json` 记下产生它时的版本(`Versions`)：tightrein 的 commit、提示与 settings 的哈希、工具与版本、模型。

### 哪些交接落盘

| 交接 | 落不落盘 |
|---|---|
| agent 给 agent | 不写：agent 之间不直接看对方的产出，都由程序转 |
| agent 给程序 | 只有结构化的 JSON 输出，程序校验并取必填事实 |
| 程序给 agent | 不写：提示在内存里拼好直接传；只在失败或调试时保存为 `prompt` |
| 程序给程序 | 同一次运行内在内存里传；只在检查点与跨阶段处落盘 |
| 给人看的 Markdown | 只有三种文档与复盘记录 |

每一步固定落盘一份 `handoff.json`：由程序写，不额外花 token；中断续跑、量化数据、复盘都从它读。它也是检查点(见 `recovery.md`)。

### 量化数据(所有步骤共用)

| 字段 | 含义 |
|---|---|
| durationMs | 耗时 |
| calls、retries、rounds | 模型调用次数、重试次数、交回修改或重出的轮数 |
| tokens | 输入、输出、缓存读取、缓存写入 |
| costUsd、costEstimated | 费用；工具不返回时按价格估算并注明 |
| filesRead、linesRead | 读取的文件数与行数 |
| filesChanged、linesChanged | 改动的文件数与行数(只适用于改代码的步骤) |
| produced | 产出条数，按步骤给出名称与数量 |
| passed、failed | 检查通过与不通过的项数 |

不适用的字段写 null，不省略。

### 必填事实(按步骤，举例)

| 步骤 | 必填 |
|---|---|
| 采集各模块 | 来源、时间窗口、读到的条数、产出的信号数、跳过或失败的来源与原因 |
| 去重 | 处理的信号数、新问题、累计、抑制、回归、判为已解决的各多少 |
| 评估 | 判定、依据的代码位置、触发条件、严重度、处理方式、代码笔记 |
| 实施·定位 | 补全的代码位置与每处一句说明 |
| 实施·方案 | 改哪些文件、每步改什么、对应哪条验收标准、不做什么 |
| 实施·编码 | 改了哪些文件与位置、与方案的偏离及原因、写了哪些测试；worktree 的 commit(`worktreeCommit`) |
| 实施·自检 | 每项检查的命令与结果 |
| 实施·审查 | 每条阻断项的位置、触发条件、原因；逐条验收标准的核对结果 |
| 发布 | PR 地址、合并提交、部署记录、验收结果 |
| 复盘 | 新建与追加的记录、各自评级 |

### 给人看的文档

一个 Issue 给人看的只有三种，都由程序从 store 与 `handoff.json` 渲染，序号 `90` 排在最后：

| 文档 | 文件 | 何时生成 | 写什么 |
|---|---|---|---|
| 待审核 | `90-issue-pending.md` | 到人工关卡 | 要决定什么、推荐与理由、不决定会怎样、确认用的命令 |
| 出问题 | `90-issue-failure.md` | 失败、卡住、超出预算、没有进展而停下 | 停在哪一步、原因、已经试过什么、建议怎么处理、接着做的命令 |
| 交付 | `90-issue-deliver.md` | 验收通过 | 修了什么、改了哪些文件、PR 与合并提交、验收结果、整个流程的量化数据 |

渲染时模型写的自由文字中的标题整体下移，代码块按 CommonMark 判断闭合，不与文档自身的小节混淆。Issue 正文与 PR 说明发到 GitHub，不算在内。

## 在哪配置

不可配置。每一步的必填字段写在那一步文件夹的 schema 中。

## 缺省值

| 项 | 缺省 |
|---|---|
| 备注长度上限 | 4000 字，超出截断并注明 |
| 状态 | `passed`、`failed`、`pending` 三种 |

## 设计依据

- **前三部分必填、备注附加**：下一步只依赖结构化部分，备注不进下一次模型调用，省 token，也防止关键事实藏在自由文字里(44 号计划「交接文档的规范」「协议层的性价比设计」)。
- **量化数据全由程序统计**：agent 自报的数字不可信；审计与复盘直接用这一份，不另记一套。
- **每步只落一份 JSON**：检查点、量化数据、复盘同出一处，人看的文档由它渲染，两边不会对不上。
- **null 不省略**：读的一方能区分「不适用」与「漏写」。
- **校验一次列出全部错误**：agent 重写一次就能改完，不必来回多轮(旧 `contracts/validate.py`)。
- JSON Schema 2020-12(https://json-schema.org/draft/2020-12/release-notes)。
