# 分诊

分诊判断问题是否成立、有多严重、值不值得修，给出处理标签。LLM 擅长写出「看起来对」的结论而不擅长保证正确，
模型之间互相复核的收益也会递减，因此分诊只保留必要的模型调用，问题是否真实存在的最终验证交给修复前的复现测试。

## 1. 环节

| 环节 | 做什么 | 实现 |
|---|---|---|
| 查重 | 判断与已有问题是否语义重复(归并已按指纹去重) | 便宜模型，只在有候选时运行 |
| 取证 | 回到代码核实问题：触发条件、影响、根因、严重度及理由；同时给出价值判断、规模(预估文件与行数)与修复方向 | 强模型，一次调用；采集时已取证的直接复用，只做一次 |
| 证伪复核 | 另一个模型专门寻找理由反驳取证结论 | 只在高风险时运行：严重度 P0、P1，以及安全、权限类问题；其余由修复前的复现测试兜底 |
| 处理标签 | 按决策树给出处理方式 | 程序 |
| 引入提交 | 用 git 找出引入问题的提交 | 程序 |

不再单独运行价值评估(并入取证)、容量分析与跨条对齐。

## 2. 处理标签(决策树)

不使用数值优先分，按决策树(参照 SSVC)由严重度、证据强弱、规模档直接给出处理标签：立即修、排期修、观察、不修。
决策树的分支与阈值放在配置中，项目可以覆盖。
