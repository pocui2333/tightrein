# 验证

AI 写的改动若由同一个模型同时写实现、写测试、做评审，一开始的误解会被测试与评审一起「证实」。因此生成与验证分开：
修复内部的自检之外，验证模块只做独立于写代码模型的检查。

取舍按能力与成本的平衡(见 05-fix.md 第 4 节的原则)：一项检查拦下的错误如果在合并或上线前再无其他环节能发现，就值得保留。

## 1. 划分

修复前复现、项目检查命令、修复后复现在修复内部完成(05-fix.md 第 5、7 步)，验证模块不再重复。

| 阶段 | 检查 | 拦下什么 | 漏过后能否被兜住 | 运行条件 |
|---|---|---|---|---|
| PR 阶段 | 项目 CI 的必需检查 | 构建、测试、类型等失败 | 合并前只有这一道 | 项目有 CI 时 |
| PR 阶段 | 其他问题的回归 | 把以前修好的问题又改坏 | 只能在部署后发现 | 总是 |
| PR 阶段 | 截图评审 | 界面错位、控件不可用等视觉问题 | 不能：前端错误上报只抓 JS 报错 | 改动涉及前端且项目配置了页面检查 |
| PR 阶段 | 本地启动服务跑接口测试 | 单元测试没覆盖到的接口 5xx 与状态码错误 | 只能在上线后由部署后确认与日常 api-fuzz 发现 | 项目配置了本地启动且改动涉及接口 |
| 部署后 | 确认问题不再出现 | 修复在真实环境中没有生效 | 最后一道 | 总是(见第 2 节) |

不对 PR 的 diff 单独跑静态巡检：合并后的日常增量巡检会审到，高风险改动在修复的深度评审中已由另一家模型审过。

## 2. 部署后确认

按问题的来源确认，全部由程序完成：

- 来自错误追踪或监控平台的：新版本中该分组不再出现并观察一段时间后标记为已解决，再出现则标记为回归并重新打开。
- 来自 api-fuzz 的：对目标环境重放当初失败的请求。
- 来自静态巡检的：对合并后的代码再运行一次对应的检查。

## 3. 自动合并的条件

修复自检通过、评审没有阻断项、PR 阶段适用的检查全部通过。
