# 发布

## 1. 分支、提交与 PR 的格式

先有通用的缺省格式；项目有自己的约定时用项目的。

**通用格式**

| 项 | 格式 | 例子 |
|---|---|---|
| 分支名 | `<类型>/<Issue 编号>-<简短描述>`，全部小写，单词以短横线连接；类型取 `feature`(新功能)、`bugfix`(修缺陷)、`hotfix`(线上紧急修复)、`chore`(杂项) | `bugfix/3-export-duplicate-key` |
| 提交信息 | 第一行 `<类型>(<范围>): <一句话>`(Conventional Commits)，一句话用项目语言；空一行后写为什么这样改 | `fix(导出): 同一主问题不同追问不再拆成两条` |
| PR 标题 | 一句完整的话，祈使语气，说清做了什么 | 把分组 key 改成不含追问的主问题 |
| PR 描述 | 不分固定小节：正文写解决什么问题、为什么选这个做法、这个做法的不足与局限；之后写关联(`Closes #编号` 与相关的 Issue、PR)；最后附上程序生成的验证结果(复现测试修复前失败、修复后通过，各项检查的结论) | — |

依据：分支名采用最常见的「类型前缀 + 工单编号 + 短横线描述」写法；通用格式不使用个人前缀，各指南不推荐以个人名命名分支，需要个人前缀的项目在工作区配置。
提交与 PR 的第一行、正文写法参照 Google 的 CL 描述规范。

**项目约定的优先级**(从高到低)

1. 工作区 project.yaml 中显式配置的格式。
2. 项目中写明的约定，自动识别：PR 模板(`.github/PULL_REQUEST_TEMPLATE.md` 及 GitLab、Bitbucket 的对应文件)、提交规范配置(例如 commitlint)、
   `CONTRIBUTING.md`、`AGENTS.md` 等文档中关于分支与提交的规定。
3. 从项目历史推断：最近的提交信息与远程分支名有明显统一的风格时沿用；推断结果在接入时交用户确认，确认后写入工作区配置，之后不再推断。
4. 都没有时使用通用格式。

## 2. 自动合并

依据：自动合并只应发生在范围窄、规则确定、可观察、可撤销的通道里；高风险改动只生成决策简报交人决定。

- **路径规则**：改动涉及 CI 工作流、依赖清单、迁移、权限认证、密钥配置等路径时，一律不自动合并，生成决策简报交用户。
  路径规则放在配置中，核心给出通用缺省，技术栈与项目可以补充。与 05-fix.md 中按任务类型限制自动合并同时生效。
- **由谁执行合并**：仓库配置了分支保护与必需检查时，开启 GitHub 原生的自动合并，由平台在检查全部通过后合并；没有分支保护时，
  由 tightrein 检查条件(见 06-verify.md 第 3 节)后合并。
- **评审结论写进 PR**：AI 评审的结论以评论或描述中的一节写入 PR，只作为说明，不作为批准。

## 3. 撤销

部署后确认发现某次合并的改动导致回归时，自动提一个撤销该合并的 PR，交用户决定；合并采用 squash，每次修复只有一个提交，撤销干净。

## 4. 部署跟踪

部署信息按平台读取，每个平台一个只读方法(例如 GitHub Deployments、Vercel)，与采集的做法一致。项目都没有配置时，以合并时间加观察期进行部署后确认。
