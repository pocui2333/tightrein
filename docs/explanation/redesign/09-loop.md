# 编排(loop)

编排把各模块串起来：定时运行、按状态推进、在需要用户时停下、汇总结果。

## 1. 原则

- **编排由程序完成**：按状态表推进，不由模型决定流程(工作流优于自由探索的 agent)。
- **崩溃后能继续**：每一步都记录下来，能从中断处继续；有副作用的步骤使用幂等键，防止重复执行。
- **审批关卡写在配置里**：模型不能在运行时自行决定是否请示，也不能绕过关卡。

## 2. 审批关卡

关卡集中定义在一张配置表中。必须交用户决定的：涉及高风险路径的合并(07-release.md 第 2 节)、删除分支或数据、修改权限与密钥配置、
超出单个任务上限、标记为需要决定(needs-decision)的 Issue。其余关卡(放行 Issue、确认计划等)按流程表与自主决定规则处理。

等待用户时暂停，不占用资源；批准后从原处继续。

## 3. 预算与熔断

- 预算分三层：每次运行、每天、每周的上限；每周上限可对应订阅额度的百分比。到达上限即停下，并写入摘要。
- 熔断：同一对象连续失败达到次数上限，或同一步骤反复重试时，停止处理该对象，转为待决定。

## 4. 待用户决定的收件箱

所有需要用户处理的事项集中到一处：每天一份汇总，列出待拍板的事项，每件附推荐做法；同时发送一条 macOS 通知。
GitHub 镜像中对应 needs-decision 标签。

## 5. 触发、顺序与并发

- 触发：工作日固定时间运行；另有两种事件触发：检测到新提交时运行增量巡检，检测到新部署时运行部署后确认。
- 顺序：按分诊的处理标签排序，先「立即修」，再「排期修」。
- 并发：同一时间默认只修复 1 个 Issue，可配置。

## 6. 暂停

`tightrein pause` 可全局或针对单个项目暂停：不再发起新的运行，进行中的步骤完成后停下；`tightrein resume` 恢复。

## 7. 运行摘要

运行摘要使用交接文档格式中的进度(progress)类型，与每天的收件箱汇总合为一份。
