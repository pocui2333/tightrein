# 交接文档

模块之间、模块内部的各角色之间，一律通过生成的 Markdown 文档交换信息、下达任务、标明进度。所有文档共用一个基础格式，
按文档类型在基础格式上变化。下游拿到的是文档的引用，按需读取，不在调用之间传递大段内容。

## 1. 基础格式

每份文档由 YAML 头信息与 Markdown 正文组成。

````markdown
---
kind: triage-result          # 文档类型，决定「内容」部分有哪些固定小节
id: TR-20261002-0003         # 唯一编号
status: done                 # pending、in-progress、blocked、done、failed
from: triage/claim-verifier  # 写入者(模块/角色)
to: fix                      # 交给谁
subject: P-0043              # 所说的对象(问题、Issue、运行等)
parent: SC-20261001-0042     # 上游文档的编号，串起整条链路
created: 2026-10-02T10:15:00+08:00
updated: 2026-10-02T10:21:00+08:00
next: fix plan 0003          # 下一步
---

## 结论
## 内容
## 需要决定
## 下一步
## 引用
## 历史
````

**头信息给程序使用**：路由、状态与链路串联，由核心写入并校验。

**正文给 AI 与人阅读**，小节固定、按顺序出现：

| 小节 | 内容 |
|---|---|
| 结论 | 1 到 3 句，最重要的结果；下游先读这一节，多数情况下读这一节即可 |
| 内容 | 按文档类型的固定小节(第 2 节) |
| 需要决定 | 拿不准、需要上级或用户拍板的问题，每条附推荐方案与理由；没有时写「无」 |
| 下一步 | 复选框清单，每项写明由谁执行 |
| 引用 | 证据、原始输出、上游文档等的路径 |
| 历史 | 只追加，每行一个时间点与事件 |

**数据块**：需要程序精确读取的数据(例如疑点列表、计划的文件清单)放在正文中带标签的代码块里，按该文档类型的 schema 校验。

## 2. 文档类型

每种类型只规定「内容」部分的固定小节，其余部分与基础格式相同。类型定义与 schema 集中在核心维护，新增类型只需定义它的小节。

| 类型 | 用途 | 「内容」的固定小节 |
|---|---|---|
| task | 上游向下游下达任务 | 目标、输入、约束、验收标准、产出要求 |
| result | 下游回报执行结果 | 做了什么、产出、证据、偏离与原因 |
| finding | 采集产出的问题 | 现象、位置、证据、严重度提示 |
| decision | 请求用户或上级拍板 | 背景、选项及利弊、推荐与理由 |
| plan | 修复或实现计划 | 方案、文件与步骤、验收对照、不做什么 |
| review | 评审意见 | 结论、问题清单(阻断或建议)、依据 |
| progress | 长任务的进展 | 检查清单、已完成、卡点 |
| issue | 本地 Issue | 问题、影响、触发条件或复现步骤、期望与实际、原因、验收标准 |

## 3. 让 AI 读得准的规则

1. 结论放在最前面。
2. 小节标题完全固定，AI 与程序都按标题定位，不改写、不换说法。
3. 一份文档只说一个对象。
4. 大数据不内嵌：日志、原始输出、长代码放在单独的文件，正文只给引用路径与摘要；正文长度有上限。
5. 编号贯穿：问题、Issue、运行、文档使用固定格式的编号，以 parent 串起链路。
6. 状态只看头信息：进度用 status 与「下一步」中的复选框表示，不写在叙述中。
7. 语言按项目配置；代码、路径与标识符保持原样；不使用表情符号。

## 4. 校验

- `tightrein doc check <文件>` 校验头信息、必需的小节与数据块的 schema。
- 每个模块与角色交接前自动校验，不通过时退回重写，不向下游传递。

## 5. 谁来写、读哪些

依据：强制模型按严格格式输出会削弱推理，先自由分析、再单独转成结构化格式几乎能找回全部损失(《Let Me Speak Freely?》，EMNLP 2024)；
上下文越长效果越差，关键信息放在开头或结尾时最好(Chroma 对 18 个前沿模型的测试)。

- **文档由程序生成，模型不手写格式**：模型只负责内容，分两步：先自由写分析(不限格式)，再输出结构化结果(schema 约束，结构化字段放在分析之后，
  或由便宜的模型单独提取)。程序用结构化结果与分析文字按文档类型的模板渲染 Markdown：头信息、固定小节、数据块、引用与历史都由程序写入，
  小节标题不会出错。
- **下游只读需要的小节**：程序按任务把相关小节摘入下游的提示，完整文档只作为引用，需要时再读。
- **关键约束放在开头**：给模型的任务文档中，目标、验收标准、注意事项放在最前面，大段背景放在后面。
- **每个小节有长度上限**：超出的部分放进单独的附件文件，正文只给引用与摘要。

## 6. 与现有交接方式的关系

模块之间的 JSON 交接文档与给人看的 Markdown 报告合并为一份文档：程序读取头信息与数据块，AI 与人阅读正文。
