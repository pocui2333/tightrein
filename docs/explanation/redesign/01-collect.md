# 采集

采集只从外部只读观察被测系统；被测系统内部的错误，一律从它已接入的平台的只读查询 API 获取。

取舍按能力与成本的平衡(见 05-fix.md 第 4 节的原则)：一种来源发现的问题如果没有其他环节能发现，就值得保留。

## 0. 方法一览与实现方式

| 方法 | 实现方式 |
|---|---|
| 内部错误(第 1 节) | 通用代码 |
| 项目规范的日志(第 3 节) | 说明文档 |
| 业务告警(第 4 节) | 通用代码 |
| 访问日志(第 1 节，可选) | 通用代码 |
| 项目探针(第 4 节) | 说明文档 |
| api-fuzz(第 5 节) | 通用代码 |
| 静态巡检(第 6 节) | 通用代码 |
| 任务外发现 | 通用代码 |

- **通用代码**：取什么、怎么判断在各项目基本一致，逻辑全部写在 tightrein 的核心与方法目录中；项目只做配置并提供所需的项目知识
  (例如 api-fuzz 的接口描述、角色能力表、测试账号、生产环境允许测试的接口清单)。
- **说明文档**：高度依赖项目的日志规范或业务规则，tightrein 只提供说明文档(契约、约束与示例)，由项目按文档自行实现；
  核心只负责调用与校验输出格式。
- 两个说明文档类的方法都以项目探针实现(项目规范的日志即读取指定类别并按项目规则判断的探针)。文档按 00-documentation.md 的格式提供：
  一份操作指南「如何编写项目探针」(附业务异常与项目规范日志两个完整示例)、一份由 schema 生成的「探针契约」参考；
  配套命令 `tightrein project probe new <名称>`(生成模板并登记)与 `tightrein project probe test <名称>`(单独试跑并校验输出)，
  以及供探针复用的辅助函数(读取钥匙串、脱敏、调用日志平台取数)。
- 各方法的具体实现(首批支持哪些平台与工具、用哪些库)在实现时联网比较后决定，按性价比选用。
- 每种方法默认不启用，项目在 project.yaml 中配置了才启用；采集只运行已配置的方法，运行摘要列出未启用的方法。

## 1. 被测系统内部的错误

**采集的种类**：只采集两种。

| 种类 | 内容 | 来源 |
|---|---|---|
| 应用运行报错 | 应用运行日志(程序经自身日志框架输出、带级别的日志)中的错误与异常，带堆栈 | 错误追踪平台(例如 Sentry)或集中日志平台(例如 ELK、OpenSearch、Grafana Loki、云厂商的日志服务) |
| 前端错误 | 用户浏览器中的 JS 报错与失败请求，带堆栈与操作轨迹 | 错误追踪平台的浏览器端 SDK |

两者带堆栈、能直接定位到代码，且通常来自同一个错误追踪平台。前端错误要还原到源码行，需要被测项目在构建时向平台上传 source map。

**可选来源：访问日志**。接口变慢、5xx 比例升高这类性能与可用性退化，除访问日志外没有其他来源能发现(api-fuzz 默认不检查响应过慢)。
项目有 APM 平台或已把网关、反向代理的访问日志送入日志平台时，可以启用：按接口统计耗时与错误比例，与此前的基线比较，明显退化时产出信号。默认不启用。

**获取方式**：只通过上述平台的只读查询 API 获取。

- tightrein 运行在使用者本机，与被测系统的服务器分开；不登录服务器读取日志文件，不在服务器上执行命令，
  不在被测系统中增加任何组件。接入错误追踪与前端埋点是被测项目自己的决定与改动。
- 查询凭证只授予读权限，存放在本机钥匙串。
- 每次按时间窗口查询上次读取之后的新增条目；平台的保留期须长于两次运行的间隔，查询发现缺口时在运行结果中写明。
- 取回的内容先脱敏再存储。
- 被测系统没有接入这类平台时，不启用这部分采集，运行时缺陷由 api-fuzz 与静态巡检发现，前端缺陷由静态巡检发现。

**方法目录**：按平台提供只读查询方法(每个平台一个)，一个项目可以选用多个；项目只选用方法并填写参数。

**格式**：错误追踪平台(含浏览器端 SDK 采集的前端错误)的 API 返回固定结构(错误类型、消息、堆栈、出现次数、影响用户数、版本、
前端另有浏览器、页面地址与操作轨迹)，读取方法将其转为统一的信号格式。集中日志平台的查询接口固定，但日志内容由各项目的打日志方式决定，
项目须另配字段映射(结构化日志指明级别、消息、堆栈等字段；纯文本日志给出解析用的正则)，复用 json-lines 与 regex 解析方法。
项目不用平台 SDK、自行上报前端错误并写入日志时，按日志平台处理。

## 2. 页面测试

采集中不做页面测试：不在采集环节启动浏览器跑页面用例，项目也不需要编写与维护采集用的页面用例。

浏览器引擎(Playwright)只用于验证环节，修复涉及前端时运行页面类复现检查与截图评审。

被测系统还没有真实用户时，前端错误平台不会有数据，这一阶段前端的运行时问题只能由静态巡检与修复时的截图评审发现。

## 3. 项目按自身日志规范记录的日志

许多项目有自己的日志规范，规定哪些事件必须记日志(例如 catch 捕获的异常、权限校验失败、数据写入与状态流转、敏感操作)。
各项目的规范不同，因此这类日志作为一种可选来源：取哪些类别、如何判断异常由项目决定，核心不预设。

可采用的做法：

- 这类日志须能经日志平台的只读查询 API 或项目提供的只读查询接口取得，获取要求与第 1 节相同；只写在服务器文件或数据库日志表中的，
  tightrein 不读取。
- 带堆栈的异常类条目(例如被 catch 捕获后只记日志、没有向上抛出的异常)按应用运行报错同样处理。
- 需要统计才有意义的类别(例如权限校验失败)按角色与接口统计，关注本应有权限却被拒绝、或拒绝次数突增的情况。
- 需要业务规则才能判断的类别(例如状态流转是否合法)由项目自己的判断规则检查。

## 4. 业务异常

许多问题不报错，只有按业务判断才知道不对，例如定时任务没有按时跑完、处理量突然为零、业务指标突降或突增、数据违反业务规则、
外部依赖即将失效(证书到期、额度用尽)。

**读取已有的业务告警**：被测系统已有监控与告警(例如 Prometheus 与 Grafana 的告警规则、云监控、定时任务监控、数据质量检查)时，
通过监控平台的只读查询 API 读取已经触发的业务告警作为信号，不重复实现告警规则。获取要求与第 1 节相同。基础设施类告警
(磁盘、内存、重启等)不读取。

**项目探针(补位)**：被测系统没有这类监控时，项目可以在工作区编写自己的探针脚本，检查只有本项目知道的业务异常。

- 位置与登记：脚本放在 `workspaces/<项目>/probes/`，在 project.yaml 中登记名称、运行命令、运行频率与所需的只读凭证(存放在本机钥匙串)。
- 接口：经标准输入、标准输出收发 JSON；输入为上次运行时间与上次留下的状态，输出为一组信号，每条含位置、现象、证据、严重度提示与指纹。
- 约束：只从外部只读观察，不修改被测系统，不登录服务器。
- 核心负责按时间表调用、校验输出格式并把信号交给归并，之后的流程与内置探针相同；查什么、按什么规则判断由项目决定。

## 5. api-fuzz

**检查项按价值分级**：默认只开启高价值的检查，其余可由项目手动开启。

| 检查 | 默认 |
|---|---|
| 服务器报错(5xx) | 开启 |
| 越权(低权限角色或匿名访问到不应访问的接口) | 开启；需要项目配置角色能力表 |
| 状态码不符(例如参数错误应返回 400 却返回 200 或 500) | 开启 |
| 响应结构不符 | 接口描述由框架从代码自动导出时开启(不符说明代码有问题)；接口描述为手写时关闭(不符多半是描述写错) |
| 响应过慢 | 关闭 |
| 不支持的方法(例如 TRACE) | 关闭 |

**按环境限制可测的请求**：生产环境只测只读方法(GET)，且只测项目明确列出允许测试的接口；会写数据的接口只在测试环境测。
配置违反这一限制时启动报错。

**接口描述的来源**：优先由框架自动导出(例如 .NET 的 Swagger)；没有时由 AI 读代码起草一份，交用户确认后存入工作区，之后随代码变化更新。

## 6. 静态巡检

**审查的模型**：增量审查与基线审查(调用点 `collect.static-review`、`collect.baseline-review`)宜路由到强模型。增量审查是新代码缺陷的主要发现者，它漏掉的问题没有其他环节会再看。

**成本**：静态巡检由确定性工具(Semgrep 等)、AI 审查(增量、基线、同类扫描)与取证组成。基线审查的费用中，取证约占四分之三，因此按以下方式控制成本：

- **按严重度决定是否在采集时取证**：高、中级疑点在采集时逐条取证；低级疑点不在采集时取证，直接进入待处理清单，
  等分诊选中或用户选中时再取证。
- **超出取证上限的疑点不丢弃**：同样进入待处理清单，后续运行继续处理。
- **取证只做一次**：采集时的取证结论交给分诊直接复用，分诊不再重复取证；只有取证结论缺少下游需要的内容时才重新取证。
- **基线审查合并小模块**：按目录分批时，文件很少的小模块在每批的文件数与行数上限内合并到同一批，减少审查调用次数。
