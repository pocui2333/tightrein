# Issue

## 1. 状态

Issue 只有六种状态：待决定、待修、进行中、待合并、完成、取消。修复内部进行到哪一步(出计划、写代码、验证等)记在修复的进度文档中，
不占用 Issue 状态。

## 2. 什么问题才建 Issue

只有分诊处理标签为「立即修」「排期修」的问题才建 Issue；「观察」的留在问题列表中，再次出现或严重度升级时再建；「不修」的直接关闭。
避免大量低价值的 Issue 淹没真正需要处理的问题。

## 3. 拆分与依赖

任务拆分出的子任务，在 GitHub 镜像中使用 GitHub 原生的子 Issue 与阻塞关系(gh 2.94 起支持 `--parent`、`--blocked-by`)，
网页上直接可见层级与先后顺序；本地 Issue 同样记录父子与依赖关系。

## 4. 与 GitHub 镜像的字段归属

按字段划分归属，避免两边互相覆盖：Issue 的开关状态以 GitHub 为准(用户在 GitHub 上关闭或重新打开会读回本地)，其余字段一律以本地为准。

## 5. 标签

本地 Issue 在头信息中记录状态与任务类型。在 GitHub 镜像上：
- **仅使用 GitHub 常规类型标签**：如 `bug`、`enhancement`、`documentation`、`security`、`refactor`、`dependencies` 等，与 GitHub 生态与开源项目标准标签命名保持一致。
- **彻底去除机器前缀与内部状态标签**：不添加 `tightrein:` 前缀，也不往 GitHub Issue 打内部生命周期状态标签（如 `needs-decision`、`open`、`in-progress` 等，状态由 GitHub 原生 Open/Closed 表达），避免污染用户仓库的标签体系。

## 6. 格式

Issue 是交接文档(00-handoff-documents.md)的一种类型，内容按 GitHub 对编码 agent 的 WRAP 建议组织：改什么与为什么、参考、验收标准、注意事项。
写得清楚的 Issue 是写代码的 agent 直接据以实现的任务说明，也是快速通道省去单独勘察与出计划的前提。

**头信息**：类型、编号、状态、严重度、任务类型、规模档、处理标签、来源、上游。

**结论**：一句话说清问题与后果。

**内容**的固定小节：

| 小节 | 内容 |
|---|---|
| 问题 | 现状与期望 |
| 影响 | 谁、什么数据受影响，范围 |
| 复现 | 触发条件或复现步骤(编号列表) |
| 原因 | 根因位置(可点击的代码链接) |
| 范围 | 可能涉及的文件；明确不在本次范围内的部分 |
| 注意事项 | 不能改的文件或行为(例如公共接口、数据结构、受保护文件) |
| 验收标准 | 可观察、可验证的复选框条目，必含：复现测试修复前失败、修复后通过；现有测试全部通过；列出必须保持不变的行为 |
| 修复方向 | 建议的做法，不强制 |

其余为基础格式的小节：需要决定、下一步、引用(完整证据折叠显示，相关的 PR 与 Issue)、历史。


## 7. 线上镜像格式（拟人化工单）

本地 Issue 文件是流水线与编码 Agent 的完整工程交接文档，而线上 GitHub Issue 是面向协作者与用户的工单展示。
为了避免线上出现浓重的“AI 机器审计与流水线转储感”，tightrein 在推送到 GitHub 时自动将内容转换为真人开发者提单的习惯结构：

| 小节 | 内容 | 说明 |
|---|---|---|
| 原因 | 触发条件、背景上下文、根因代码链接 | 说明为什么会有这个 Issue，代码位置自动换为取证 commit 永久链接 |
| 问题 | 现象描述、期望与实际表现、复现步骤 | 清楚阐述遇到了什么问题，以及如何复现 |
| 方法 | 解决思路、修复方向建议、涉及文件 | 供开发者参考的修复思路与主要改动文件 |

在转换中彻底剥离内部控制指令(如 `approve` 审批命令)、流水线测试复选框、机器约束与水印声明；完整证据与引用折叠在 `<details>` 中，保留隐藏的 HTML 标记用于双向对齐。

同时，**彻底屏蔽内部决策结论与流水线评论**：诸如「需要用户决定：复杂度为中，高于低」、「自动放行：...」、「修复计划已确认」等自治决策与流水线状态流转，一律保留在本地 Issue 历史记录与 CLI 运行摘要中，不再向 GitHub Issue 追加结论评论。线上 Issue 仅在关联 PR 创建/合并或关闭时保留必要说明。
