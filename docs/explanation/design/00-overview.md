# 0. 总体结构

采集 → 聚合去噪 → 分诊取证 → 提 Issue → 生成修复 → 验证 → 合并发布 → 观测学习，最后一步的结果再回到采集。

横切能力：编排调度、权限隔离、审计与总开关。

模块之间只通过约定好的中间产物交互，依次是：信号(Signal)、问题(Problem)、Issue、PR。这样换一个项目时只需替换采集器和检查命令。

## 0.1 定位与约束

这是一个个人工作辅助工具，不是被测项目的团队功能。文档中的例子取自一个虚构的 ASP.NET Core + Vue 项目，称为「示例项目」，工作区为 `workspaces/demo/`。

- **零侵入**：不在被测系统及其仓库中增加任何东西，包括 SDK、工作流、`data-testid`、工具目录和配置项。
- **外部观测**：探针在系统外部运行，通过网络访问 staging，与普通用户看到的一样；对仓库只读，只用于导出接口描述和静态分析。
- **Issue 在本地，PR 以本人身份提**：发现的问题记录为本地 Issue，不发布到 GitHub；修复以用户本人的 GitHub 身份提 PR，遵守该项目的 Git 协作流程和 AGENTS.md(分支前缀、提交确认等)；PR 由用户本人审核，认可就合并、不认可就关闭，本工具不执行合并。
- **代码与数据位置**：本工具的代码、配置、信号数据、本地 Issue 和本文档都放在个人目录 `~/Projects/tightrein/`，不进入被测项目仓库。
- **可以使用的外部条件**：staging 的数据允许被测试污染；可以在 staging 上以普通用户的方式创建测试账号。
