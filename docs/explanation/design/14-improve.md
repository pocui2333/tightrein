# 14. 自我改进只建议

当前设计见 [redesign/08-learn.md](../redesign/08-learn.md)。

## 14.1 职责与原则

自我改进改进的是工作流本身(提示词与模型档)，而不是被测项目；它只做建议，不自动修改：

- 从近期的失败中归纳对提示词或模型档的修改建议，附评测用例的对比结果，写成决定文档进收件箱；用户批准后由用户自己应用，程序没有
  合入补丁、修改配置的执行路径。
- **不能只凭自我反思修改自己**：没有外部反馈时，模型的自我纠错会退化。每条建议都要有出问题的真实记录作依据，并在评测用例上对比。
- **自我修改会走捷径，也可能被污染**：有研究记录过自改 agent 伪造测试通过的日志、删除检测标记，也有研究用被污染的评测集诱导自改
  agent 演化出有害指令。因此评测必须包含未参与改进的用例，评分以确定性检查为主，评测集与评分器不可改，改动由用户批准并留在 git 历史中。
- 编排不自动运行自我改进：评测要多次运行模块，费用高，由用户执行 `tightrein learn improve` 决定何时运行。

## 14.2 环节效益

每个调用 LLM 的环节都要用产出证明自己值得保留。各模块调用执行器之后登记一条环节效益记录(`stage_yield`：环节、角色、对象、
实际使用的工具与模型、token、费用)，学习回填结果已确定的有效产出，周报按(环节、角色)汇总：调用次数、token、费用、有效与无效的数量、
每条有效产出的 token、最近一次有效产出之后的调用次数。

**有效产出**按环节定义，只计入结果已经确定的调用；结果还未确定的(例如 Issue 尚未关闭)不计入分子也不计入分母：

| 环节 | 有效产出 |
|---|---|
| 静态巡检的初筛 | 初筛给出的主张经取证判为成立，且没有被用户改判为误报 |
| 分诊取证 | 判定没有被用户改判，且没有被 3.10 判为误判 |
| 证伪复核 | 复核改变了最终判定，且用户认可改变后的判定 |
| 修复勘察、计划与实施 | 修复通过合并前验证，且 PR 被合并 |
| 修复评审(轻量与深度) | 提出的不通过项被修正后通过检查，且没有被用户推翻 |
| 截图评审 | 指出的布局问题被修正 |
| 知识写入去重判断 | 判断为 `update`、`merge` 或 `noop`，避免了重复条目 |
| 经验撰写 | 经验条目在之后的任务中被命中 |
| 缺陷变规则 | 规则通过验证收入规则库 |
| 改进建议 | 建议被用户批准 |

确定性检查、边界检查与用户关口不计算环节效益，它们不调用 LLM。

## 14.3 出问题的来源

改进只从出问题的记录中取材料，与经验总结(8.5)共用同一份来源：分诊误判、评审驳回(PR 要求修改、修复评审不通过的轮次)、
修复失败(转人工)、被撤销、用户驳回修复计划、用户关闭 Issue。最近 `thresholds.learn.improve.lookbackDays` 天内的来源少于
`minTroubles` 条时不调用模型。

## 14.4 建议与评测

1. `improvement-writer` 读取出问题的来源，归纳一条有共同原因的建议，没有共同原因时不给建议。建议的对象只有两种：
   - **prompt**：修改 `skills/` 下某个环节的角色说明或参考资料，给出统一格式的补丁；
   - **model**：某个环节改用另一个能力档。
2. **校验**：prompt 类补丁只能改 `skills/` 下的文件，且不触及评测、边界与自我改进本身；model 类的能力档要对应一个不同于当前的模型。
3. **评测**：用该环节的评测用例对比当前版本与候选(prompt 类以当前 HEAD 加补丁为候选，model 类以候选能力档的模型为候选)，
   每个用例每个变体运行 `repeats` 次。用例来自 `evals/` 中封存的用例与运行即评测保存的真实用例(8.7)，分为两组：
   - 参与改进：来源对象在建议针对的对象或出问题的来源中；
   - 未参与改进：其余用例，少于 `minHeldOutCases` 个时不出建议并写明原因，而不是降低要求。
4. **推荐**：评分以确定性检查(代码判定的条目)的通过率为主。评测完整、未参与改进的用例没有变差、参与改进的有提升时推荐批准，
   否则推荐拒绝并写明原因。
5. **决定文档**：`data/improve/<建议编号>.md`(decision 类型：背景是出问题的来源与两组的对比表，选项为批准与拒绝，附推荐与理由，
   引用补丁 `data/improve/<建议编号>.patch` 与评测报告)，建议记录 `improvement` 进收件箱。

## 14.5 批准之后

`learn accept <建议编号>` 只记录决定并在决定文档的历史中写下批准；应用由用户自己完成：prompt 类在本工具仓库用 `git apply` 应用补丁
并提交，model 类在工作区配置中修改能力档。拒绝时写明原因，同一对象在没有新证据时不再生成同样的建议。

## 14.6 可以改与不可以改的范围

| 可以建议 | 不可以改 |
|---|---|
| `skills/` 下各环节的角色说明与参考资料 | 评测集与评分器(`evaluation/`、`evals/`) |
| 某个环节使用的能力档 | 安全边界：第 11 章的工具白名单、禁止事项、受保护文件(`guards/`) |
| — | 所有人工审批与确认的环节，以及自我改进本身(`pipeline/improve/`) |

补丁触及右列任何内容，直接不出建议。

## 14.7 参考

- Anthropic《Demystifying evals for AI agents》：代码评分、模型评分、人工评分的取舍；评结果不评路径；评分器要防绕过。
- 无外部反馈时自我纠错会退化(Huang 等，ICLR 2024)；LLM 评审的位置偏好、篇幅偏好与自我偏好(MT-Bench 研究)。
- Claude 4 系统卡：写死值、针对测试特判属于奖励投机，可以用隐藏测试检测，提示中明确禁止能显著降低发生率。
- 自改 agent 的教训：Darwin Gödel Machine 伪造测试通过的日志、删除检测标记，靠可追溯的版本记录发现；被污染的评测集会诱导自改 agent
  演化出有害指令。
- Agent Skills 最佳实践与 skill-creator：同时运行改动前后两组做对比，警告不要针对测试用例过拟合(因此必须有未参与改进的用例)。
- Anthropic 的多 agent 研究系统：多 agent 的 token 消耗约为单次对话的 15 倍，编码类任务收益有限；据此以环节效益决定环节的去留。
