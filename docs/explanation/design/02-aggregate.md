# 2. 聚合去噪

## 2.1 职责与边界

把四个探针产出的零散信号合并成「问题」(Problem)，过滤掉环境故障、偶发抖动和已确认不处理的噪声，只把值得分诊的问题交给下游。

- **输入**：各探针写入的信号(1.3 统一格式)。
- **输出**：问题记录，以及本次状态为「新发现」或「回归」的问题清单。
- **不做的判断**：两个指纹不同的问题是否实为同一根因、问题是否值得修，都由分诊模块判断。本模块是确定性的 Python 脚本，不调用 LLM，同样的输入永远得到同样的结果。

## 2.2 触发与并发

- 每个探针运行结束后调用一次聚合，只处理本次运行新写入的信号。
- 多个探针可能同时结束，聚合入口先获取文件锁 `data/aggregate.lock`，同一时间只有一个聚合在执行，后来者排队等待。
- SQLite 开启 WAL 模式并设置 busy timeout，探针写信号与聚合读信号互不阻塞。
- 聚合可以重放(`aggregate --rebuild`)：先备份数据库，清空 `problems` 相关的表，按时间顺序把 `signals` 全部重新聚合一遍，得到的结果与增量聚合一致，问题编号按信号重合度继承。指纹规则调整后用这种方式重建。

## 2.3 处理流程

1. 规范化(2.5)：清洗消息与位置中的易变部分。
2. 抑制规则(2.9)：命中人工抑制规则的信号直接标记为已抑制，不再往下走。
3. 计算指纹(2.6)，归并到问题：指纹已存在则追加到该问题，否则新建问题。
4. 复现确认(2.7)：新建的问题按来源做复现确认。
5. 状态更新(2.8)：更新本次涉及的问题，以及本次运行覆盖范围内但没有再出现的问题。
6. 输出(2.13)。

## 2.4 健康检查

采集前的健康检查(`target.healthcheck`，示例项目中的取值为匿名接口 `GET /api/Health`)不通过时，跳过本次采集并在运行摘要中写明，
不产出信号(redesign/02-aggregate.md 第 2 节)。登录失败的角色不产出信号，由链路健康检查提醒用户处理测试账号。聚合不再判定
环境问题，也不暂扣「疑似整体故障」的信号。

## 2.5 规范化

按顺序对 `message` 和 `location` 做替换，把易变的部分换成占位符：

| 内容 | 替换为 | 例子 |
|---|---|---|
| GUID | `<guid>` | `3f2a...-9c1e` |
| ISO 时间与 `HH:mm:ss` 时间 | `<time>` | `2026-09-29T02:15:03Z` |
| 连续 4 位以上的数字 | `<num>` | 订单号、自增 ID |
| 十六进制串(8 位以上) | `<hex>` | 哈希值、commit |
| 临时文件与上传路径 | `<path>` | 示例项目中的例子：`D:\app\...\upload\...` |
| 引号内的用户输入值 | `<value>` | 校验消息中回显的非法参数 |

- 规范化后截断到 200 个字符。
- `location` 统一为路由模板、页面路由模板或 `文件:类名.方法名`，不带行号；示例项目中的例子为 `/api/Material/{id}`、`/material/detail/:id`。
- 内置的默认规则由核心的 `domain/normalize.py` 执行，项目特有的规则放在工作区的 `normalize.yaml`(示例项目为 `workspaces/demo/normalize.yaml`)。

## 2.6 指纹

**计算方式**：来自错误追踪平台、监控平台的信号直接使用平台自己的分组编号作为指纹(写成 `<平台>:<编号>`，如
`sentry:acme/4512`、`alertmanager:9f2c…`)，不自行计算。其余来源按下表把字段拼成一个规范字符串，取 SHA-1 的前 16 位；不使用
行号。每条指纹规则带有版本号，规则调整后版本号加一，并按 2.2 重放重建。

| 来源 | 指纹组成 |
|---|---|
| api-fuzz | `check` + HTTP 方法 + 路由模板 + 状态码类别(如 5xx)+ 角色(仅越权检查) |
| 内部错误(日志平台)，有堆栈 | 异常类型 + 堆栈中前 3 个本项目帧(类名.方法名)；哪些帧属于本项目由 `log-parse` 扩展判定，示例项目中的取值为命名空间 `Demo` 下的帧 |
| 内部错误(日志平台)，无堆栈 | 日志类别 + 规范化后的消息 |
| 访问日志 | 退化类型 + HTTP 方法 + 路由 |
| 项目探针 | 探针名 + 探针在输出中给出的指纹 |
| static | 缺陷模式或规则名 + 文件 + 类名.方法名 |
| incidental | 文件 + 类名.方法名 + 规范化后的发现摘要 |

**取舍说明**

- 越权检查的指纹带上角色，因为同一接口对不同角色越权是不同的缺陷；其他检查不带角色，同一接口的 5xx 不论哪个角色触发都视为同一个问题。
- 堆栈只取本项目的帧，框架与第三方库的帧会随版本变化，也和根因无关。
- 静态巡检不用行号，别人在同一文件里增删代码会改变行号，但问题还是同一个。为此静态巡检的信号必须带上所在方法，`location` 写成 `文件:类名.方法名`。

## 2.7 复现确认

只对新建的问题做复现确认，确认前问题处于「待确认」状态，不交给分诊。

| 探针 | 做法 | 判定 |
|---|---|---|
| api-fuzz 服务端错误(`not_a_server_error`) | 按信号中的 `reproduce` 重放(`thresholds.reproduceAttempts`，缺省 2 次) | 至少 1 次复现为有效；都没有复现则保持待确认并标记「间歇出现」，不再重放 |
| api-fuzz 其他检查 | 对照接口描述与权限模型的确定性判定，采集时已判定 | 直接视为有效 |
| 内部错误、业务告警、访问日志、项目探针 | 平台与探针记录的是已经发生的事实 | 直接视为有效 |
| static | 静态巡检已由 `claim-verifier` 取证 | 直接视为有效 |
| incidental | 没有经过取证，不做复现确认 | 直接视为有效，由分诊取证 |

标记「间歇出现」的待确认问题之后某次运行再次出现时，转为新发现交给分诊。

## 2.8 问题状态

| 状态 | 含义 |
|---|---|
| 待确认 | 新建，等待复现确认 |
| 新发现 | 确认有效，尚未处理 |
| 持续 | 已交给分诊或已有 Issue，仍在出现 |
| 已解决 | 修复已部署，并且之后的覆盖运行中没有再出现 |
| 回归 | 已解决的问题在更新的版本中再次出现 |
| 已忽略 | 用户手动忽略，按 2.9 的条件恢复 |

**状态转换**

| 从 | 到 | 条件 |
|---|---|---|
| 待确认 | 新发现 | 复现确认有效 |
| 待确认 | 待确认(标记间歇) | 重放未复现 |
| 待确认(标记间歇) | 新发现 | 之后某次运行再次出现 |
| 新发现 | 持续 | 分诊模块已处理(提了 Issue 或判为暂不处理)，之后再次出现 |
| 新发现、持续 | 已解决 | 同时满足：当前部署的 commit 晚于问题最后出现时的 commit；此后至少 3 次覆盖运行没有再出现 |
| 已解决 | 回归 | 在晚于「解决时 commit」的版本中再次出现 |
| 任意 | 已忽略 | 用户手动忽略 |

**覆盖运行**：只有真正测到了问题所在位置的运行，才算作「没有再出现」的证据。

- api-fuzz：本次运行包含该接口，并且用到了问题所涉及的角色。浅跑只测 GET，不能作为写接口问题的解决证据。
- 内部错误、业务告警、访问日志、项目探针：本次运行从问题所属的来源(错误追踪平台、日志平台、告警平台、访问日志或该探针)读到了数据。
- static：扫描范围包含该文件；新 commit 上同一规则在同一方法中不再命中，即判为已解决，不需要等 3 次。

**参照 Sentry 的「在下一个版本中解决」**：旧版本上残留的出现不算回归，必须出现在比解决时更新的版本上才算回归。

## 2.9 人工操作与抑制规则

用户通过命令行操作问题，每个操作都写入 `problem_events` 留痕：

| 命令 | 作用 |
|---|---|
| `ignore <问题> --reason <原因> [--until <条件>]` | 忽略问题。恢复条件可选：到某个日期、再出现 N 次、出现在新版本中；不给条件即永久忽略 |
| `false-positive <问题> --reason <原因> [--expires <日期>]` | 判为误报，同时生成一条抑制规则，以后同指纹的信号直接抑制；到期日期缺省为当天加 `thresholds.suppressionDays` |
| `merge <问题A> <问题B>` | 把 B 并入 A，B 的指纹作为 A 的别名，以后 B 指纹的信号都归到 A |
| `reopen <问题>` | 重新打开已解决或已忽略的问题 |

抑制规则存放在工作区的 `suppressions.yaml`(示例项目为 `workspaces/demo/suppressions.yaml`)，每条规则写明匹配条件(指纹，或者探针加消息正则)、原因、添加日期和到期日期。到期的规则自动失效，避免抑制规则只增不减。

## 2.11 与 Issue 的衔接

- 问题记录中保存对应的本地 Issue 编号，由提 Issue 模块回写。
- 已有 Issue 的问题再次出现时，只累计出现次数和最近出现时间，不重复交给分诊。
- Issue 与问题状态的同步规则见 4.7。

## 2.12 存储

SQLite 数据库文件 `data/tightrein.db`，主要的表如下；全部表与列见 `docs/explanation/architecture/01-foundation.md` 4.2：

| 表 | 主要字段 |
|---|---|
| `runs` | 运行 ID、采集方法、开始与结束时间、目标 commit、覆盖范围(接口、角色、文件列表、读到数据的来源)、健康检查结果 |
| `signals` | 1.3 的全部字段、运行 ID、规范化后的消息、指纹、是否被抑制 |
| `problems` | 问题 ID、指纹、指纹规则版本、探针、标题、状态、首次与最近出现时间、首次与最近出现的 commit、解决时的 commit、出现次数、Issue 编号 |
| `problem_signals` | 问题 ID、信号 ID |
| `problem_aliases` | 问题 ID、别名指纹(合并产生) |
| `problem_events` | 问题 ID、时间、事件(状态变化、人工操作)、原因 |
| `triage_results` | 分诊结论，字段见 3.8 |
| `issues` | 本地 Issue 的索引，字段见 4.3，可从 `issues/` 下的文件重建 |

`runs` 表记录的覆盖范围，就是 2.8 判定「覆盖运行」的依据。

## 2.13 输出

- **给分诊模块**：本次状态变为「新发现」或「回归」的问题，每个附上最近一条信号、出现次数、首次出现的 commit，以及同一问题下不同角色或参数的信号样本(最多 5 条)。
- **运行摘要**：新发现、回归、已解决各有多少，列出新发现和回归问题的标题，附在探针的运行摘要之后，通过本机通知发出。

## 2.14 保留与清理

- `signals` 保留 90 天；超过 90 天的信号删除，问题记录与计数保留。
- 已解决超过 90 天、且没有关联 Issue 的问题，连同其关联记录一并删除。
- 原始报告目录(`data/runs/<运行编号>/raw/`)保留 30 天。

## 2.15 参考

- Sentry 的事件分组：优先级依次为自定义指纹、堆栈、异常类型与消息、纯消息；堆栈分组只看属于应用本身的帧；消息多变，只作兜底。
- Sentry 的问题状态：「在下一个版本中解决」会等新版本部署后才把再次出现判为回归；归档可以设置恢复条件(到期、出现次数达到 N 次等)。
- LangChain 的自愈流水线：分组前去掉 UUID、时间戳和长数字串，并截断到 200 个字符。
- Slack 等团队处理不稳定测试的做法：用重跑和运行历史区分不稳定与真实失败，按一段窗口内的失败比例判定。
