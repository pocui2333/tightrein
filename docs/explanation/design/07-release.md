# 7. 合并发布

## 7.1 职责与边界

把验证通过的修复按项目的约定送进 `main`：提交、同步主干、推送、提 PR，然后跟踪评审、合并和部署，直到部署后确认完成，最后清理工作区。分支、提交与 PR 的格式、自动合并、撤销与部署跟踪的整体设计见 [redesign/07-release.md](../redesign/07-release.md)。

- **PR 缺省由用户审核并合并**：用户在 GitHub 上审核 PR，认可就合并，不认可就关闭。本工具只读取 PR 的最终结果：已合并就完成 Issue 并继续后续环节，被关闭就说明这个修复不被采纳。项目可把关卡 `gates.merge` 设为 `auto`(适合个人项目)，由本工具或 GitHub 在 PR 满足全部合并条件后合并(7.6)。
- **生产发布不在范围内**：`master` 对应正式生产环境，由团队按自己的流程发布。本工具只记录修复是否已进入 `master`。
- **每个 git 写操作都单独确认**：执行前说明命令、分支、文件、影响和能否撤销，用户同意后才执行，同意只对这一次操作有效。汇总见 7.10。项目可把关卡 `gates.release-writes` 设为 `auto`，建修复分支、本地提交、合并主干、推送修复分支、创建或更新 PR、发评审评论、提撤销 PR 直接执行，执行结果照常记录；高风险操作不受影响(7.10)。

## 7.2 提交

1. **前置条件**：Issue 为「进行中」且处于提交阶段，即合并前验证已通过；修复最后一轮的确定性检查(5.2 第 4 步，含项目的交付规则)全部通过，且此后工作区没有新改动。不满足时按项目规则列出未通过的检查项、位置和问题，由用户决定先处理(`fix apply <Issue 编号> --review-only` 或 `fix start`)，还是照常提交(`release commit <Issue 编号> --accept-findings`，被接受的未通过项写进 Issue 历史与 PR 描述)。
2. **生成提交信息**：按项目约定(本节末的「格式与约定」)生成；通用格式为 Conventional Commits：第一行 `<类型>(<范围>): <一句话>`，空一行后写为什么这样改。类型由任务类型映射(`git.commitTypes`)，范围、一句话与原因由写代码的模型给出(用项目语言)。
3. **生成文件清单**：列出本次改动的文件，按文件名排序。缺陷修复受 5.5 改动上限约束，一次提交即可。
4. **确认后执行**：把提交信息和文件清单交给用户确认，确认后执行 `git add -- <文件>` 和 `git commit -F <提交信息文件>`；提交信息写成文件传入，不经命令行转义。

**格式与约定**：分支名、提交信息与 PR 先有通用格式，项目有自己的约定时用项目的。优先级从高到低：工作区 `project.yaml` 的 `git.conventions`；项目中写明的约定(PR 模板、commitlint 配置、`CONTRIBUTING.md`、`AGENTS.md`、`CLAUDE.md` 中的模板)；从项目历史推断(只给结果，接入时交用户确认)；通用格式。通用的分支名为 `<类型>/<Issue 编号>-<简称>`(类型由任务类型映射，立即修的 P0 为 `hotfix`)，个人前缀只在 `git.personalPrefix` 为真或项目模板要求时加，且不得是 AI 或工具名称(`git.forbiddenPrefixes`)。

## 7.3 同步主干

推送前检查 `main` 是否有新提交：

1. `git fetch origin`(只读)，比较修复分支与 `origin/main`。
2. `main` 没有新提交：直接推送。
3. `main` 有新提交：把 `origin/main` 合并进修复分支(`git merge --no-ff --no-edit origin/main`)，使用 merge，不使用 rebase(rebase 须由用户主动提出)。合并前先确认工作区干净。
4. **有冲突**：处理时每个冲突文件说明两侧的改动和取舍，同一功能存在互斥实现时交用户选择，不自行保留某一侧。用户解决冲突后执行 `release sync <Issue 编号> --continue`，确认后完成合并提交；放弃合并执行 `release sync <Issue 编号> --abort`，确认后执行 `git merge --abort`。
5. 合并了 `main` 之后，重新执行一次合并前验证(6.3)，通过后才推送。

## 7.4 推送

- 说明目标远程分支和将要推送的 commit，确认后执行 `git push -u origin <分支>`。
- 推送被拒绝时停下，说明原因，不使用 `--force`。通常是远程有新提交，回到 7.3。

## 7.5 提 PR

1. **检查分支名**：必须符合项目约定的分支格式，个人前缀不能是 AI 或工具名称。分支在 5.3 中按同一约定生成，这一步是复核；不符合时给出建议名称。
2. **标题**：一句完整的话，祈使语气，说清做了什么；由写代码的模型给出，没有时取 Issue 标题。
3. **描述**：不分固定小节。正文三段写解决什么问题、为什么选这个做法、这个做法的不足与局限；之后写关联(`Closes #<编号>` 与父 Issue、前一个子任务)；最后附程序生成的验证结果(复现测试修复前失败、修复后通过，各项检查的结论，照常提交时接受的未通过项)。项目有 PR 模板时按模板的标题把同样的内容放进对应段落，认不出的标题与模板中的复选框原样保留。
4. **确认后创建**：标题、描述和目标分支(`main`)交用户确认后，执行 `gh pr create`，返回 PR 链接。分支已有打开的 PR 时，只在描述有变化时生成 `gh pr edit` 更新描述，同样先确认。
5. **回写**：Issue 记录 PR 链接，状态改为「待合并」，通知用户去审核。修复评审的结论以评论写入 PR(7.6)。

## 7.6 审核与合并

PR 创建后 Issue 为「待合并」。本工具在每次定时运行时只读查询 PR 状态(`gh pr view --json state,mergeable`)，按结果处理：

| PR 状态 | 含义 | 处理 |
|---|---|---|
| 已合并 | 修复被合并 | Issue 改为「完成」(关闭原因为已修复)，等待部署后确认：部署跟踪(7.7)、部署后确认(6.4)、生产发布记录(7.8) |
| 已关闭且未合并 | 用户认为这个修复不行 | Issue 以「修复未采纳」取消；关联的问题转为「已忽略」，恢复条件为严重度升级或在新版本中再次出现；计入 8.3 的 PR 被拒率。用户在 PR 上留有说明的，原文追加到 Issue 的「历史」 |
| 仍然打开 | 尚未处理 | 超过 3 个工作日在运行摘要与周报中提醒；出现冲突时通知用户，按 7.3 在本地合并 `main` 解决，不在网页上解决冲突 |

**评审结论写进 PR**：PR 创建后，修复最后一轮 AI 评审的结论以评论发到 PR(`release.reviewComment`，缺省开启)，注明只作说明、不是批准；同一轮评审只发一次。

**自动合并**(`gates.merge: auto`)：自动合并只发生在范围窄、规则确定、可观察、可撤销的通道里。

- **路径规则**：改动命中 `release.autoMergeBlockPaths`(核心缺省覆盖 CI 工作流、依赖清单与锁文件、迁移、权限认证、密钥配置，技术栈与项目可追加)时一律不自动合并，生成决策简报 `data/fixes/<编号>/merge-decision.md` 交用户决定(合并、补充评审后合并、关闭 PR)。与修复按任务类型对自动合并的限制同时生效。
- **共同条件**：PR 阶段适用的检查全部通过(本机检查通过、CI 必需检查没有失败，design 6.1)；修复评审没有未处理的阻断意见(最后一轮检查全部通过，且没有以 `--accept-findings` 接受的未通过项)；PR 头部就是本工具最近一次推送的 commit。
- **由谁合并**：主分支有分支保护或规则集的必需检查时，开启 GitHub 原生的自动合并(`gh pr merge --auto`，只开启一次)，由平台在检查全部通过后合并；没有时由本工具另外检查 PR 不是草稿、没有冲突、必需检查与必需评审都已满足(`mergeStateStatus` 为 CLEAN)、没有人「请求修改」，全部满足后合并。合并用 `--squash`(`release.mergeMethod` 可改为 merge)并删除远程修复分支，带 `--match-head-commit` 防止判断之后出现的新提交。
- 任一条件不满足就不合并、照常等待，原因列在运行摘要「自动决定」与 Issue「历史」中。

用户想让修复改一改再合并时，自己执行 `fix start <Issue 编号>`，把修改要求作为输入，修改后重新走验证、提交和推送，PR 自动更新。

## 7.7 部署跟踪

PR 合并后，`main` 的新提交由项目的部署平台部署到 staging。部署信息按平台读取，经扩展点 `deploy-source` 选用一个只读方法：`core/github-actions`(按工作流查 GitHub Actions 运行)、`core/github-deployments`(GitHub Deployments)、`core/vercel`(Vercel)。示例项目使用 `core/github-actions`，工作流为 `deploy.yml`。

1. 在方法返回的部署记录中查找包含该合并提交的部署：先找 commit 相同的最新一次；它被跳过(例如部署等待窗口内有更新的提交，由最新一次统一部署)时，找 commit 包含它的最早一次。
2. **部署成功**：触发部署后确认(6.4)。
3. **部署失败**：立即通知用户并附上部署链接。`main` 部署失败必须马上处理，因为 staging 坏了会挡住所有人；是不是本次修复引起的由用户判断，需要修复时新开分支，走完整流程。
4. **没有配置部署来源**：合并时间加 `release.deploy.observationHours`(缺省 24 小时)之后视为已部署，再做部署后确认。
5. **手动部署的部分**：改动匹配 `target.manualDeployPaths` 的(示例项目中为 `src/compute/`)，Issue 中提示用户联系负责人手动更新。

部署后确认通过后，本工具起草一句「已在测试环境验证通过」及验证摘要，交用户确认后由用户回复到 PR 中。

## 7.8 生产发布记录

定期只读检查修复的合并提交是否已进入 `origin/master`(`git branch -r --contains <commit>`)。进入后在 Issue 的「历史」中记录日期，不做其他操作。

## 7.9 收尾清理

Issue 完成且部署后确认通过后，提示用户执行 `fix cleanup <Issue 编号>`，由用户主动发起清理：

1. 说明将要执行的命令：删除该 Issue 的 worktree(`git worktree remove`)，删除本地修复分支(`git branch -d`)，清理已删除的远程分支记录(`git fetch --prune`)。
2. 删除分支须由用户主动提出，并说明风险后二次确认。`git branch -d` 只会删除已经合并的分支，未合并时会拒绝执行，风险较低；远程分支在合并 PR 时删除。
3. 复现检查(工作区 `regressions/`)不随清理删除，继续作为回归测试。

## 7.10 git 写操作确认汇总

| 操作 | 所在环节 | 确认方式 |
|---|---|---|
| 建分支、建 worktree | 5.3 | `approve` 时单独确认；`gates.release-writes: auto` 时直接执行 |
| `git add`、`git commit` | 7.2 | 确认提交信息与文件清单；`gates.release-writes: auto` 时直接执行 |
| 合并 `origin/main` 进修复分支 | 7.3 | 单独确认(`gates.release-writes: auto` 时直接执行)；有冲突时逐个文件确认取舍，冲突解决后的合并提交与放弃合并各自单独确认 |
| `git push` | 7.4 | 确认目标分支与 commit；`gates.release-writes: auto` 时直接执行(只推送修复分支) |
| `gh pr create`、`gh pr edit` | 7.5 | 确认标题、描述与目标分支；`gates.release-writes: auto` 时直接执行 |
| 在 PR 上发评审结论评论 | 7.6 | 确认评论内容；`gates.release-writes: auto` 时直接执行 |
| 删除 worktree 与本地分支 | 7.9 | 用户主动发起，二次确认 |
| 合并 PR 并删除远程修复分支，或开启 GitHub 自动合并 | 7.6 | 缺省由用户在 GitHub 上操作；`gates.merge: auto` 时满足全部条件后由本工具执行 |
| 提撤销合并的 PR(建分支、`git revert`、推送、`gh pr create`) | 7.12 | 确认后执行；`gates.release-writes: auto` 时直接执行；撤销 PR 不自动合并；部署后确认发现回归时自动提出(6.4) |
| 关闭 PR | 7.6 | 用户在 GitHub 上操作，本工具不执行 |
| GitHub Issue 镜像的建立、标签、关系、评论、开关(4.11) | issue | 缺省逐次确认；`gates.mirror-writes: auto` 时直接执行 |

`gates.release-writes`、`gates.merge` 与 `gates.mirror-writes` 相互独立(关卡表见 architecture/09 3.8)。删除修复 worktree 与本地分支属于必须交用户的关卡 `delete`，改动命中高风险路径的合并属于 `high-risk-merge`。force push、`reset --hard`、rebase、`commit --amend`、冲突解决后的合并提交与放弃合并、直接向主分支提交或推送，永远不在关卡表的放行范围内：本工具不生成前四种，其余仍按上表由用户发起或确认。

## 7.11 输出

- Issue 回写：提交的 commit、PR 链接、评审记录、合并时间、部署记录、进入 `master` 的日期。
- 运行摘要中列出：等待用户确认的 git 操作、待合并的 PR、可以合并的 PR、需要用户决定是否合并的 PR(决策简报)、部署失败的记录。

## 7.12 撤销合并

部署后确认发现某次合并的改动导致回归时，提一个撤销该合并的 PR 交用户决定：`release revert <Issue 编号> --reason <原因>` 生成待确认操作，从 `origin/main` 建分支(类型 `hotfix`，描述 `revert-<简称>`)，`git revert` 合并提交(合并方式为 merge 时加 `-m 1`)，推送并创建 PR(标题「Revert: <原 PR 标题>」，描述写原因、原 PR 与 Issue)，不自动合并。合并采用 squash 时每次修复只有一个提交，撤销干净。撤销不改变 Issue 状态，执行结果记进 release 交接文档与 Issue 历史。
