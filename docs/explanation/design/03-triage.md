# 3. 分诊取证

## 3.1 职责

对聚合交来的每个问题回答四件事：它是真的吗、根因在哪、是谁的哪次提交引入的、值不值得修，并给出处理标签。然后决定它的去向：提 Issue、等待部署、忽略、判为误报，或者交给用户人工判断。整体设计见 [redesign/03-triage.md](../redesign/03-triage.md)。

分诊只读代码、只出结论，不改代码，也不对外发布任何内容。

## 3.2 分诊的组成

分诊由核心编排，下列角色各自经 agent 执行器独立运行。每个角色的说明是 `skills/triage/references/roles/` 下的一个文件，调用时作为执行器任务的 `instructions`，与所用工具无关。模型档见 9.6。

| 角色 | 职责 | 输出 | 模型档 |
|---|---|---|---|
| `claim-verifier` | 在代码中核实一条主张是否成立：找到相关代码、读懂实际逻辑、找出触发条件、找反证(追到入口，看上游有没有挡住)；响应过慢类问题同样由它取证。一次调用同时给出价值判断、任务类型、预估改动与修复方向 | 先写自由分析(`analysis`)，再写结构化字段：四档判定(确认成立、条件成立、不成立、证据不足)、带 `文件路径:行号` 的代码事实、触发条件、反证检查(每条写明入口位置与上游校验的结果)、影响面、任务外发现；判为成立或条件成立时另有评估(`assessment`)：价值判断(该修、可修可不修、暂不修、不该修)与理由、任务类型、预估改动的文件与行数(不含测试文件)、修复方向、需用户定夺的标记、暂不修时的重估条件 | 强档 |
| `refuter`(证伪核实者) | 只在高风险时运行的独立复核(3.4 第 2 步)，任务是专门寻找理由反驳取证结论 | 同 `claim-verifier` | 强档 |

**核心负责的部分**

- **组装输入**：按 3.3 把问题转成主张。给角色的只有任务、路径和已核实的事实，不给判断与倾向。
- **证据质量检查**：全部由代码执行，取证之后不另设模型评审。检查项与 12.2 分诊的验收标准一致：每条证据的 `文件路径:行号` 在取证 commit 上真实存在；条件必填字段齐全；不含「可能」「大概」「建议进一步排查」等含糊措辞；判定不成立时，现象来源指向真实存在的代码位置或主张中的某条事实；反证检查至少追到一个入口，每条写明入口位置与上游有无校验。未通过的，把逐项原因交回同一角色重做，最多重做 2 次(12.3)；仍不合格的判为「证据不足」并进入人工队列。判定本身对不对，由高风险问题的证伪复核(3.4)、修复前的复现测试(5.6)、用户改判(3.9)与效果反馈(3.10)校准。此外，成立时评估不能为空，预估的已有文件须在取证 commit 上存在，暂不修须写重估条件。
- **处理标签**：不使用数值优先分，按决策树由判定、严重度、规模档与价值判断给出处理标签(3.5)。
- **单独标出三类问题**：取证的评估给出标记：根因在设计本身、局部修补无法根治的；修复要动数据结构或存量数据的；修复会改变公共实现或接口契约的。这三类在发现报告与 Issue 中单独标出，修复时须先由用户定夺。
- **结构化输出**：每个角色都按 `outputSchema` 返回 JSON，核心校验后写入数据库；发现报告由结构化结论渲染生成。

**无人值守**：分诊中不向用户提问。需要业务量级、现象细节、范围边界等只有用户知道的信息时，直接判为「证据不足」并进入人工队列，由用户补充信息后重新分诊。

## 3.3 输入：把问题转成主张

分诊遵循「给任务与路径，不给结论」：交给角色的只有观察到的事实，不带聚合阶段的推测。

| 探针 | 主张模板 | 附带的事实 |
|---|---|---|
| api-fuzz 5xx | `<角色>` 调用 `<方法> <路由>`，传入 `<输入>` 时服务端返回 `<状态码>` | 请求与响应摘要、复现命令、关联的服务端异常堆栈 |
| api-fuzz 越权 | `<角色>` 不具备 `<能力>`，调用 `<方法> <路由>` 却返回了 `<状态码>` | 端点要求的 Policy、角色能力矩阵中的对应行 |
| api-fuzz 契约不符 | `<方法> <路由>` 的响应与接口描述不一致：`<差异>` | 接口描述片段、实际响应片段 |
| api-fuzz 响应过慢 | `<方法> <路由>` 在 `<输入>` 下耗时 `<毫秒>` | 多次耗时记录 |
| e2e 用例失败 | `<角色>` 在 `<页面>` 执行 `<步骤>` 时失败：`<错误>` | 失败步骤、截图路径、trace 路径 |
| e2e `console_error` / `failed_request` | `<页面>` 加载时出现 `<报错或失败请求>` | 报错原文、请求与响应摘要 |
| 内部错误 | 服务端(或浏览器端)抛出 `<异常类型>`：`<消息>` | 堆栈中本项目的帧、出现次数、影响用户数、操作轨迹 |
| static | `<文件:类名.方法名>` 存在 `<缺陷模式>` | `claim-verifier` 在静态巡检时已给出的证据 |
| incidental | `<文件:类名.方法名>` 存在以下问题：`<发现原文>` | 来源报告中的上下文 |

## 3.4 处理流程

1. **查重**：查询本地未关闭的 Issue 和已经分诊过的问题，由 agent 判断是否与本问题属于同一根因。属于同一根因的，把本问题作为别名并入已有问题(2.9 的 `merge`)，流程结束。
2. **取证**：在只读 worktree 中运行，代码切换到 `main` 的最新 commit，因为修复最终要提交到 `main`。
   - `claim-verifier` 判定为成立、条件成立、不成立或证据不足，定位到根因所在的 `文件:行号`，成立时一并给出评估(3.2)。每个问题只取证一次。
   - 证伪复核只在高风险时运行：取证判为成立或条件成立，且命中 `triage.refute`(严重度 P0、P1，任务类型 security，影响类别权限、数据归属，任一即可)；或预估严重度为 P0 的问题被判为「不成立」。`refuter` 只拿到同样的主张和事实，看不到第一次的判定。两次一致时采用取证结论；取证成立而复核不成立或证据不足时进入人工队列；取证不成立而复核成立时采用复核结论并进入人工队列。其余问题由修复前的复现测试兜底。
   - static 类在静态巡检时已经取证，带评估的直接复用；采集时的取证没有评估的视为不可复用，重新取证。incidental 类没有经过取证，与缺陷类一样交给 `claim-verifier`。
3. **确认 `main` 上是否仍存在**：问题发现于 staging 部署的 commit，而 `main` 可能已经更新。如果根因代码在 `main` 上已被修改，查看对应的提交；已经修复的，去向判为「等待部署」。
4. **归因**：对根因代码执行 `git blame` 和 `git log`，找出引入问题的提交、作者和对应的 PR。这些信息写进 Issue，便于找到最了解这段代码的人。
5. **判断值不值得修**：取自取证评估中的价值判断。命中工作区已接受取舍条目(`knowledge/tradeoff/`)的，直接判为「已接受的取舍」。
6. **评级与定去向**：按 3.5 评定严重度与规模档并给出处理标签，按 3.6 决定去向。

## 3.5 严重度、规模档与处理标签

**严重度**：按「不修会怎样」定级，由取证角色按下表与项目说明(`project.yaml` 的 `triage.severityGuide`)给出并写明理由(`report.severity`、`severityReason`，规则正文在 `skills/triage/references/severity.md`)。同一类问题在不同项目、不同范围下可以是不同级别：只影响个人或本机、能事后修复的数据问题一般不到 P0。

| 等级 | 含义 | 例子 |
|---|---|---|
| P0 | 线上不可用、数据丢失或泄露、安全漏洞 | 越权读写、跨公司看到数据、静默丢弃用户数据、凭证泄露、主流程整体不可用 |
| P1 | 核心功能错误，或数据长期错误但有替代办法 | 核心报表持续算错但可人工核对；登录、提交计算、查看结果某一步失败需绕路 |
| P2 | 非核心功能错误，或偶发 | 非核心接口 5xx、响应字段与描述不符、少见输入才出现的错误 |
| P3 | 轻微 | 控制台报错但功能正常、响应偏慢、依赖存在低危漏洞、文案 |

取证没有给出 `report`(旧结论)时按影响类别映射：权限、数据归属、数据正确性、凭证泄露为 P0，核心流程不可用为 P1，非核心出错与契约不一致为 P2，其余为 P3。

**规模档**：按取证评估中预估改动的文件数与行数(不含测试文件)分为微、小、中、大、超限五档，门槛见 13.1；没有评估时取根因文件、行数为 0。
规模档与任务类型决定修复走哪条通道(5.2)。

**处理标签**：按决策树 `triage.treatment.rules`(参照 SSVC)给出立即修、排期修、观察、不修四种之一，门槛与缺省规则见 13.2。

## 3.6 去向

| 分诊结论 | 去向 | 问题状态 |
|---|---|---|
| 不成立 | 判为误报，生成一条带到期日期的抑制规则。P0 问题须经过 3.4 第 2 步的独立复核 | 已忽略 |
| 命中已接受的取舍 | 记录原因 | 已忽略 |
| `main` 上已经修复 | 等待部署后由聚合模块判定已解决 | 持续 |
| 成立，处理标签为立即修或排期修 | 交给提 Issue 模块起草 Issue | 持续 |
| 成立，处理标签为观察 | 暂不修：记录理由；再出现 N 次或严重度升级时重新分诊，之前判为观察而再次判为观察的升为排期修并提 Issue | 已忽略 |
| 成立，处理标签为不修 | 记为已接受的取舍，理由写明处理标签，不自动恢复 | 已忽略 |
| 证据不足，或证伪复核要求转人工 | 放进人工队列，由用户判断 | 新发现 |

P0 问题只要判定为成立或条件成立，一律交给提 Issue 模块；运行摘要的等待事项中处理标签为立即修的置顶，再按严重度排序。预估改动触及受保护文件的 Issue 带「需要先与代码作者讨论」标签。

过滤得越激进，越容易把真问题一起丢掉。因此自动判为误报的问题，每周在运行摘要中汇总列出一次，供用户抽查。

## 3.7 运行方式

- 由 agent 执行器以无人值守、只读的方式在只读 worktree 中执行，加载本工具的 `triage` skill 与 3.2 中的角色说明。
- 只开放读取、搜索和只读 git 命令。agent 不能写文件，发现报告与结构化结论作为结果交回，由本工具保存。
- 分诊在聚合之后执行。每次最多分诊 5 个问题，按严重度预估排序：越权与 5xx 优先，static 与 P3 类在后，剩下的留到下一次。
- 每个问题只分诊一次，结果按指纹缓存。只有以下情况才重新分诊：问题回归、出现了新类型的证据(例如新关联上一条服务端异常)、用户手动要求。

## 3.8 输出

每个问题产出两份结果：

- **发现报告**：按 `triage` skill 中的发现报告模板生成，存放在 `data/findings/<问题ID>.md`，供用户阅读，也是提 Issue 和生成修复的依据。
- **结构化结论**：写入数据库的 `triage_results` 表。

| 字段 | 说明 |
|---|---|
| 问题 ID | 对应的问题 |
| 判定 | 成立 / 条件成立 / 不成立 / 证据不足 |
| 严重度、规模档、处理标签 | 3.5 的评级 |
| 任务类型 | 取证评估给出的八种之一：缺陷、安全、数据、前端、功能、重构、依赖、文档配置 |
| 根因位置 | `文件:行号`，可以有多处 |
| 引入提交 | commit、作者、PR 编号 |
| 去向 | 3.6 中的一种 |
| 理由 | 一段话，说明判定与去向的依据 |
| 分诊时的 commit | 取证时 `main` 的 commit |
| 复核结论 | 触发独立复核时的第二次判定 |
| 实际结果 | 3.10 中的一种，事后回填 |

运行摘要中列出本次分诊的每个问题：标题、判定、严重度和去向。人工队列中的问题单独列出。

## 3.9 用户介入

- 用户可以查看任意问题的发现报告，改判其结论(`retriage <问题> --verdict <判定> --reason <原因>`)，改判记录写入 `problem_events`。
- 人工队列中的问题由用户逐个处理(`triage queue` 列出)：补充信息后用 `retriage <问题> --note <补充信息>` 重新分诊，或直接改判；判定后按 3.6 的去向继续流转。

## 3.10 效果反馈

记录每条分诊结论后来的实际结果，用来衡量分诊判得准不准：

| 实际结果 | 判定依据 | 说明 |
|---|---|---|
| 判对 | 本地 Issue 完成并通过部署后确认；或判为误报的问题在之后的运行中不再出现 | 分诊结论与实际一致 |
| 误判为成立 | 本地 Issue 被用户以「不是缺陷」关闭，或修复 PR 被团队以「不是缺陷」「无法复现」等理由拒绝 | 分诊把没问题的判成了有问题 |
| 误判为不成立 | 判为误报的问题，后来被用户在抽查中改判，或者以其他方式被证实为真问题 | 分诊漏掉了真问题，比误判为成立更严重 |
| 用户改判 | 用户用 `retriage` 修改了结论 | 记录改判前后的结论和理由 |

- 实际结果写入 `triage_results` 的「实际结果」字段，运行摘要每周给出一次准确率：按判定类型和探针类型分别统计。
- 误判的案例整理成一条条分诊经验(哪类现象容易被误判、误判的原因)，每条经验是工作区 `knowledge/triage-lesson/` 下的一个知识条目，经写入去重(16.7)后由 `learn` 直接写入；调用分诊时由核心按标签预取，作为额外上下文提供给 agent(16.6)。

## 3.11 参考

- Sentry Seer：为每个问题给出「可操作性」评分，只对高分问题自动做根因分析和修复；自动化的门槛还包括最近 14 天内出现 10 次以上。
- LangChain 的自愈流水线：Triage Agent 先建立「代码改动 → 错误」的因果联系，只有改动涉及运行时代码、并且因果关系明确时才放行，结论带置信度和理由。
- Sentry 内部的自动化调试流程：根据根因代码的提交历史找出最熟悉该代码的工程师，请他来审查。
- 关于 LLM agent 过滤误报的对比研究(Sifting the Noise)：agent 能把 OWASP Benchmark 上超过 92% 的误报率降到 6.3%，但过滤得太激进会把真漏洞一起压掉。
