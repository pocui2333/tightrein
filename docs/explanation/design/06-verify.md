# 6. 验证

## 6.1 职责

证明修复确实生效，并且没有弄坏别的地方。验证只做独立于写代码模型的检查(redesign/06-verify.md)：修复前复现、项目检查与修复后复现在修复内部完成(5.2 第 5、7 步)，验证不再重复。

| 阶段 | 检查 | 拦下什么 | 运行条件 |
|---|---|---|---|
| PR 阶段 | 项目 CI 的必需检查 | 构建、测试、类型等失败 | 主分支有必需检查时，PR 创建后由发布跟踪读取，作为自动合并的条件(7.6) |
| PR 阶段 | 其他问题的回归 | 把以前修好的问题又改坏 | 总是：采用修复第 7 步的结果，需要服务的检查在本机服务上补跑 |
| PR 阶段 | 截图评审 | 界面错位、控件不可用等视觉问题 | 改动涉及前端且配置了页面检查(`page-routes` 或工作区的 e2e 用例) |
| PR 阶段 | 本机启动服务跑接口测试 | 单元测试没覆盖到的接口 5xx 与状态码错误 | 配置了本机启动(`local-run`)且改动涉及接口 |
| 部署后 | 确认问题不再出现 | 修复在真实环境中没有生效 | 总是(6.4) |

不对 PR 的 diff 单独跑静态巡检：合并后的增量巡检会审到。验证由确定性的程序执行，不需要 LLM 参与判断；只有截图需要用户或 agent 查看。

## 6.2 本机启动方式

所有验证都通过核心的本机启动过程启动服务(`docs/explanation/architecture/07-fix-verify-release.md` 第 11 章)。启动什么、怎样启动由 `local-run` 扩展点给出(`docs/explanation/architecture/10-extensions.md` 3.8)：扩展按 worktree、启动模式与端口返回启动计划，核心按计划启动、判断就绪、收尾。启动过程的做法采用 2026-09-18 那次运行中实际跑通的方式(由原 `browser-verify.md` 迁移到 `verify` skill 的 `references/local-run.md`)。

| 项 | 通用做法 |
|---|---|
| 启动计划 | `local-run` 给出每个服务的命令、工作目录、非敏感的环境变量、端口、就绪信号与失败信号，以及不在本机启动的服务与迁移文件的路径模式。连接配置由被测程序自己读取，核心、扩展与 agent 都不读取任何配置文件和凭证 |
| 迁移检查 | 启动前检查修复是否改动了迁移文件。没有改动，启动时不会执行任何新迁移；有改动，启动会把新的迁移应用到测试库，停下向用户说明将执行哪几条、能否撤销，确认后再启动 |
| 就绪判断 | 同时匹配成功信号和失败信号，避免崩溃时一直等到超时 |
| 启动模式与端口 | 只需要后端的验证(API 类复现检查、接口回归)用 `api` 模式，端口取 `localRun.ports.api`；需要页面的验证用 `page` 模式，后端与前端端口取 `localRun.ports.backendForPages`、`localRun.ports.frontend`。启动前检查端口，被占用时不强行启动，页面类检查记为「未验证」，并通知用户空出端口后重跑 |
| 不在本机启动的服务 | 依赖这些服务的流程在 PR 阶段记为「未验证」，部署后确认时再验证 |
| 没有 `local-run` | PR 阶段不启动服务，接口与页面类检查留到部署后确认 |
| 收尾 | 验证结束后停止本次启动的全部进程，日志保存到验证报告目录 |

**示例项目中的取值**(技术栈扩展 `aspnetcore` 加示例项目的项目扩展，见 `docs/explanation/architecture/10-extensions.md` 5.7、6.7)

| 项 | 取值 |
|---|---|
| 后端 | 在修复 worktree 中以 `ASPNETCORE_ENVIRONMENT=Development` 执行 `dotnet run`。Development 环境连接的是 CN 测试库，与 staging 是同一个库，staging 的数据允许被测试写入 |
| 前端 | `page` 模式下在 `src/vue` 执行 `npm run serve` |
| 迁移文件 | `Migrations/MigrationList.cs`，有改动时启动会把新的 ChangeSet 应用到测试库 |
| 就绪与失败信号 | 成功为 `Now listening on`、`Application started`；失败为 `Unhandled exception`、`error CS` 等 |
| 端口 | `api` 模式后端监听 `http://localhost:5100`，不占用开发常用的 5000 端口，与用户自己正在运行的服务互不影响；`page` 模式前端开发服务器的代理目标在 `vue.config.js` 中固定为 5000，因此后端监听 5000、前端监听 8080 |
| 不在本机启动的服务 | Python 计算服务。依赖它的流程(提交计算、查看计算结果等)在 PR 阶段记为「未验证」 |

## 6.3 PR 阶段的本机检查

`verify local` 在修复 worktree 中执行：

1. **其他问题的回归**：修复第 7 步已在修复 worktree 上运行与本次改动相关的其他 Issue 的复现检查(静态类与测试类)，这里采用其结果，不重跑。
2. **是否启动服务**：没有配置 `local-run`，或改动既不涉及接口、也不涉及前端(或没有配置页面检查)时不启动服务，跳过的检查与原因写进报告。
3. **接口测试**：启动修复后的服务(6.2)，运行本 Issue 与相关其他 Issue 的接口与页面类复现检查，对本次改动涉及的接口用 Schemathesis 浅跑一遍(`--include-path` 限定到这些接口的路由)。修复前就存在的问题不计失败。
4. **截图评审**：改动涉及页面且配置了页面检查的，执行覆盖这些页面的巡检用例并截图，由 `fix-reviewer` 的截图评审(调用点 `verify.screenshot-review`)或用户查看，只判断遮挡、错位、溢出。只看 DOM 发现不了这类布局问题。

**结论分三档**：

| 档 | 含义 |
|---|---|
| 验证通过 | 执行了，并有证据：检查结果、截图 |
| 弱证据 | 执行了，但前置条件不满足，例如页面上没有可以触发问题的数据 |
| 未验证 | 没有执行，逐条列出本应验证的具体行为和原因 |

把弱证据写成验证通过，等同于伪造检查通过。

**去向**：

- 没有失败项：Issue 进入提交阶段，进入提 PR 环节。「未验证」与弱证据的条目写进 Issue 和 PR 描述。
- 有失败：Issue 退回「待修」，验证报告作为下一次 `fix start` 的输入。同一个 Issue 连续两次验证失败，转为「待决定」(4.6 的 `hold`)。

## 6.4 部署后确认

PR 合并后 Issue 即为「完成」，等待部署后确认。部署检测发现包含该修复的 commit 已部署(没有配置部署来源时，合并后经过观察期视为已部署，7.7)后，按问题的来源确认，全部由程序完成：

| 来源 | 确认方式 |
|---|---|
| api-fuzz、e2e(接口与页面类复现检查) | 对目标环境重放当初失败的请求或用例 |
| 静态巡检与修复第 5 步(静态类与测试类复现检查) | 只读 worktree 切到部署 commit 后重跑对应的检查 |
| 错误追踪或监控平台(服务端日志)，以及复现检查无法给出结论的问题 | 部署后观察期(`thresholds.verify.observationHours`，缺省 48 小时)内不再出现即为已解决，再出现即为回归 |

- 全部确认通过：Issue 转为最终完成，同步关联问题并回填分诊结果，起草 PR 回复。
- 有回归：先生成撤销这次合并的 PR(7.12，待确认操作，交用户决定是否合并)，Issue 重新打开为「待修」，历史中记录部署 commit 与证据。
- 其余(检查未执行、观察期未满)：下次运行继续确认，超过 `thresholds.verify.stagingWaitDays` 时提醒。

## 6.5 运行方式

| 命令 | 作用 |
|---|---|
| `verify local <Issue 编号> [--confirm-migration]` | 执行 PR 阶段的本机检查；修复改动了迁移文件时第一次运行停下说明将应用的迁移，用户确认后带 `--confirm-migration` 重跑 |
| `verify staging <Issue 编号>` | 执行部署后确认；由部署检测自动触发，也可以手动执行 |
| `verify screenshots <Issue 编号> --ok\|--issue <说明>` | 截图评审给出「无法判断」，或所用工具不能读取图片时，由用户给出截图的查看结论；`--issue` 计为失败项 |

## 6.6 输出

- 验证报告：`data/verify/<Issue 编号>/<日期>-<阶段>/report.md`，包括每一步的命令与结果、三档结论、截图、服务日志。
- Issue 的「历史」一节追加验证摘要；「未验证」的条目单独列出。
