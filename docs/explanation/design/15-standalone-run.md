# 15. 每一步单独运行

## 15.1 原则

每个模块都按「纯任务」设计：

- **输入明确**：只从交接文档、数据库或命令行参数读取输入，不依赖上一步留在内存或会话中的任何东西。
- **输出明确**：只产出交接文档、数据库记录与人读文档，不留下隐含状态。
- **重跑安全**：对同一个对象重跑，结果覆盖上一次的结果，不追加、不重复；对外的操作(git、PR、通知)按幂等键去重。
- **编排不藏逻辑**：`loop` 只按状态和时间表依次调用各模块的子命令，所有判断都在模块内部。编排能做的，用户在终端里逐条执行子命令也能做到。

## 15.2 统一的命令形态

每个模块一个子命令，参数形式一致：

```
tightrein <模块> [--select <选择器>] [--input <交接文档>] [--output <目录>] [--dry-run] [--runner <工具>] [--model <模型>]
```

| 参数 | 作用 |
|---|---|
| `--select` | 选择要处理的对象，见 15.3 |
| `--input` | 直接给一份交接文档作为输入，不从数据库取，见 15.4 |
| `--output` | 结果只写到指定目录，不写数据库、不产生对外操作，见 15.5 |
| `--dry-run` | 只列出将要做什么，不执行 |
| `--runner`、`--model` | 临时指定本次使用的 agent 工具与模型，覆盖 `project.yaml` |

## 15.3 选择器

| 写法 | 含义 | 例子 |
|---|---|---|
| 对象 ID | 只处理这一个对象 | `tightrein triage --select P-0042` |
| 状态 | 处理某个状态的全部对象 | `tightrein triage --select status:新发现` |
| 探针 | 只处理某个探针产出的对象 | `tightrein aggregate --select probe:api-fuzz` |
| 运行 | 只处理某次运行产出的对象 | `tightrein aggregate --select run:R-20260929-021503-collect-api-fuzz` |
| 下游链 | 从某一步开始，连同它的下游一起跑 | `tightrein run --select triage+ --subject P-0042`：对 P-0042 依次执行分诊与提 Issue |
| 上游链 | 连同它的上游一起跑 | `tightrein run --select +aggregate --probe api-fuzz`：先跑 api-fuzz，再聚合 |

上下游链参照 dbt 的图选择写法：`+` 写在模块名后表示包含下游，写在前面表示包含上游。

## 15.4 两种输入来源

| 来源 | 用法 | 适用场景 |
|---|---|---|
| 数据库 | 默认。按选择器从数据库取对象，读取上游写入的交接文档 | 日常运行 |
| 文件 | `--input <交接文档>`，直接给一份符合 schema 的 JSON | 上游还没实现或不想运行上游时；调试某一步；评测(architecture/03 2.3)；复现一次历史运行 |

文件输入与数据库输入经过同样的 schema 校验。任何一步都可以拿一份手写或从历史中复制出来的交接文档单独运行，不需要先把上游跑一遍。

## 15.5 输出与副作用

| 模式 | 写交接文档 | 写数据库 | 对外操作(git、PR、通知、Issue 文件) |
|---|---|---|---|
| 正常 | 是 | 是 | 按各模块的确认规则执行 |
| `--output <目录>` | 写到指定目录 | 否 | 否 |
| `--dry-run` | 否 | 否 | 否，只列出将要执行的内容 |

`--output` 模式相当于沙箱：结果完整生成，但不影响真实状态。评测运行器(architecture/03 第 2 章)就是以这种模式运行各模块。

## 15.6 前置条件

每个模块声明自己的前置条件。不满足时停止，并说明缺什么、应该先运行哪个命令：

| 模块 | 前置条件 | 不满足时的提示 |
|---|---|---|
| `collect` | staging 健康检查通过(api-fuzz、e2e)；只读 worktree 已切换到目标 commit(static) | 「staging 不可用」或「先执行 `tightrein worktree sync`」 |
| `aggregate` | 有尚未聚合的信号 | 「没有新信号」 |
| `triage` | 对象状态为「新发现」或「回归」，或用户以 `retriage` 指定 | 「P-0042 已分诊，重新分诊请用 `retriage`」 |
| `issue` | 分诊结论的去向为「提 Issue」 | 「P-0042 的去向是等待部署，不创建 Issue」 |
| `fix` | Issue 状态为「待修」，修复 worktree 已创建 | 「先执行 `issue approve 7`」 |
| `verify local` | Issue 为「进行中」且处于合并前验证 | 「先执行 `fix done 7`」 |
| `release` | Issue 为「进行中」且处于提交阶段 | 「先执行 `verify local 7`」 |
| `learn` | 无 | — |

在 `--output` 模式下可以用 `--ignore-state` 跳过状态检查，便于调试与评测；正常模式下不能跳过。

## 15.7 重跑与幂等

- **交接文档**：按「模块 + 对象」唯一确定，重跑时覆盖；上一次的结果改名保留为 `<文件名>.<序号>`，便于对比。数据库按同样的键更新，不插入重复记录。
- **聚合**：同一条信号只会被归并一次；指纹规则调整后按 2.2 整体重放。
- **对外操作的幂等键**：

| 操作 | 幂等键 | 已存在时 |
|---|---|---|
| 创建 Issue | 根因位置 | 追加问题到已有 Issue(4.5) |
| 建分支与 worktree | Issue 编号 | 复用已有的分支与 worktree |
| 提交 | Issue 编号 + 改动内容的哈希 | 没有新改动时不提交 |
| 提 PR | 分支名 | 已有 PR 时只更新描述 |
| 通知 | 事件类型 + 对象 + 日期 | 同一天同一事件只通知一次 |

- **锁**：每个对象一把锁，同一对象同一时间只有一个模块在处理；聚合另有全局锁(2.2)。

## 15.8 外部依赖可以替换

单独运行某一步时，它依赖的外部系统都可以替换成可控的版本：

| 依赖 | 替换方式 |
|---|---|
| agent 工具 | `--runner replay --replay-from <运行编号或目录>`：回放一份录制好的会话记录与结构化结果，不调用任何模型，结果完全确定 |
| staging | `--target <地址>`：指向另一个环境，例如本机启动的服务 |
| 项目仓库 | `--commit <commit>`：在指定 commit 上运行 |
| 当前时间 | `--now <时间>`：用于测试按时间判断的逻辑，例如「已解决」判定、到期的抑制规则 |

回放模式使每一步都能写成确定的自动化测试：给定输入交接文档和录制的 agent 结果，断言输出的交接文档与数据库变化。

## 15.9 各模块的输入输出

| 模块 | 输入 | 输出 | 单独运行的例子 |
|---|---|---|---|
| `collect` | 目标环境配置、探针类型 | 信号 | `tightrein collect --probe api-fuzz --level shallow` |
| `aggregate` | 信号 | 问题、状态变化、关联 | `tightrein aggregate --select run:R-20260929-021503-collect-api-fuzz` |
| `triage` | 问题 | 分诊结论、发现报告 | `tightrein triage --input handoff/aggregate-P-0042.json --output /tmp/t1` |
| `issue` | 分诊结论 | 本地 Issue | `tightrein issue create --select P-0042` |
| `fix` | Issue、发现报告 | worktree 中的改动、修复报告 | `tightrein fix start 7` |
| `verify` | Issue、复现检查、worktree | 验证报告 | `tightrein verify local 7 --dry-run` |
| `release` | Issue、验证报告、worktree | 提交、PR、部署跟踪记录 | `tightrein release pr 7 --dry-run` |
| `learn` | 数据库、日志 | 指标、周报、经验、规则库、学习建议 | `tightrein learn report --now 2026-10-05` |
| `learn improve` | 出问题的来源、评测集 | 改进建议(decision 文档与补丁)、评测报告 | `tightrein learn improve --days 30` |

## 15.10 按用户的要求判断进度并继续

除了逐条执行子命令，用户也可以直接说要做什么，由 `loop` 判断现在处在哪一步，然后把后续步骤接着做完。例如：

- 「继续修 7 号」
- 「那个材料查询 500 的问题现在怎么样了」
- 「把昨天发现的问题都处理一下」
- 「7 号一直做到提 PR」

**进度就是状态**：每个问题、每个 Issue 在数据库中都有状态(2.8、4.6)，每一步的结果都在交接文档里。所以「现在在哪一步」直接从状态读出，不需要另外记录进度。这与 Anthropic 长时运行 agent 的做法一致：每次开始时先读取进度记录与 git 历史来确定当前位置，而不是依赖上一次会话的记忆。

**处理过程**

1. **识别对象**：从用户的话中找出要处理的对象。
   - 有编号的直接取(「7 号」「P-0042」)。
   - 没有编号的，按标题、接口路由、页面、文件名、时间在数据库中检索(「材料查询 500」「昨天发现的」)。
   - 匹配到多个候选时，列出候选让用户选，不自行猜测。
2. **识别目标**：用户说了做到哪一步的(「一直做到提 PR」)，以此为终点；没说的，做到下一个需要用户确认的关口为止。
3. **读取当前状态**，按下表确定下一步：

| 对象与状态 | 下一步 | 能否自动继续 |
|---|---|---|
| 问题：待确认 | 复现确认(`aggregate`) | 能 |
| 问题：新发现、回归 | 分诊(`triage`) | 能 |
| 问题：已分诊，去向为提 Issue，但还没有 Issue | 创建 Issue(`issue create`) | 能 |
| 问题：人工队列 | 向用户展示发现报告与缺少的信息，等用户补充或改判 | 否 |
| Issue：待决定 | 向用户展示 Issue，等用户放行(`issue approve`)；带 `hold` 的先说明原因，用户确认后 `fix start --force` | 否 |
| Issue：待修 | 开始修复(`fix start`) | 能，进入交互会话 |
| Issue：进行中(修复) | 续接修复会话；执行器支持时续接原会话，否则新开会话并提供已有的修复计划与当前 diff | 能，进入交互会话 |
| Issue：进行中(合并前验证) | 合并前验证(`verify local`) | 能 |
| Issue：进行中(提交) | 提交、推送、提 PR(`release`)，每个 git 写操作逐次确认 | 能，逐次确认 |
| Issue：待合并 | 提醒用户去审核，给出 PR 链接 | 否 |
| Issue：完成(等待部署后确认) | 跟踪部署，部署后做部署后确认(`verify staging`) | 能，但要等部署完成 |
| Issue：完成、取消 | 展示关闭原因与历史 | 无后续步骤 |

4. **执行并汇报**：按顺序执行，每完成一步汇报一句；到达终点、遇到需要用户确认的关口，或者某一步失败时停下，说明停在哪里、为什么停、下一步是什么。

**中断后恢复**：因为每一步都可以重跑(15.7)，运行中途被打断(电脑休眠、进程退出)后，再说一次「继续」即可。`loop` 发现某个对象有开始记录而没有结束记录，就从这一步重新执行。

**从某一步重来**：用户说「7 号从分诊重新来」时，对关联问题执行 `retriage`，下游的 Issue、修复与验证结果标记为过期，然后按上表继续。过期的结果保留，不删除。

**对应的命令**

| 命令 | 作用 |
|---|---|
| `tightrein next <对象>` | 只显示当前状态与下一步，不执行 |
| `tightrein continue <对象> [--until <模块>]` | 从当前状态继续，做到指定模块或下一个关口 |
| `tightrein continue <对象> --from <模块>` | 从指定模块重来 |

在 agent 工具中用自然语言提出要求时，`loop` skill 负责第 1、2 步的理解，再调用上面的命令；判断下一步用的是固定的状态表，不由模型自由发挥。

## 15.10 参考

- 函数式数据工程(Maxime Beauchemin)：任务应当是纯的、确定的、幂等的；重跑时覆盖而不是追加，失败或逻辑变更后可以放心重算。
- Airflow 的任务设计实践：每个任务只负责一件事、可以单独重跑；用 upsert 代替 insert 避免重复；从指定分区读取，而不是读「最新」数据；在高风险操作前设检查点。
- dbt 的节点选择：`--select` 选择单个节点，`+` 表示包含上游或下游。
- Anthropic 长时运行 agent 的 harness：每个会话开始时先读取进度文件与 git 日志确定当前位置，再继续下一项工作。
