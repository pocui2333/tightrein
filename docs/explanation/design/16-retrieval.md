# 16. 知识检索

## 16.1 要解决的问题

随着运行时间变长，工作区中的文件会持续增加：缺陷模式、已接受的取舍、分诊与修复经验、发现报告、Issue、修复报告、验证报告、周报。agent 查找信息时如果靠逐个打开文件，会越来越慢，也越来越容易漏掉相关条目，或者把过时的条目当作依据。

本章的方案分两部分：代码与知识分开检索；知识的检索以结构化存储和全文索引为主，只在评测证明不够时才引入向量检索。

## 16.2 代码与知识分开

| 对象 | 检索方式 | 理由 |
|---|---|---|
| 被测项目的代码 | agent 按需探索：`rg`、glob、读文件、git 命令 | 代码随时在变，按需探索永远是最新的，不需要维护索引；Claude Code 早期试过 RAG 加本地向量库，后来改为这种方式，效果更好也更简单；Codex CLI 与 Antigravity CLI 同样以 `rg`、glob 为主 |
| 本工具积累的知识 | 16.3 到 16.7 的方案 | 条目数量持续增长，需要按类型、状态、时间过滤，也需要识别过时条目 |

## 16.3 分层存放

| 内容 | 存放 | 原因 |
|---|---|---|
| 有状态、有字段的记录：信号、问题、分诊结论、Issue 元数据、运行记录、经验条目与缺陷模式的元数据 | SQLite | 按字段过滤、排序与统计，不需要读正文 |
| 需要人读的长篇正文：缺陷模式说明、经验正文、发现报告、Issue 正文、各类报告 | markdown，带 YAML frontmatter | 人要读、要改 |
| 交接文档 | JSON 文件，同时写入 SQLite | 第 10 章 |

**每个 markdown 文件都有 frontmatter**，至少包括：

| 字段 | 说明 |
|---|---|
| `id` | 唯一编号，其他文件以编号引用它 |
| `type` | 类型：`defect-pattern`、`tradeoff`、`triage-lesson`、`fix-lesson`、`finding`、`issue`、`fix-report` 等 |
| `tags` | 标签：涉及的目录、接口、页面、技术点、同义词 |
| `summary` | 一句话摘要，检索结果只返回这一句 |
| `status` | `active`、`superseded`(被新条目取代)、`archived` |
| `supersededBy` | 被哪个条目取代 |
| `updated` | 最近更新日期 |
| `reviewBy` | 复核日期，过了这个日期需要确认是否仍然有效 |
| `related` | 相关条目的编号列表 |

索引脚本扫描全部 frontmatter，同步进 SQLite 的元数据表。frontmatter 缺字段或格式错误时，索引脚本报错并列出文件，不静默跳过。

## 16.4 索引

**全文索引**：SQLite FTS5，对标题、摘要、标签、正文建索引，用 `bm25()` 排序，列权重为标题 10、摘要 5、标签 5、正文 1。FTS5 能精确命中编号、错误码、接口路由、类名方法名，这些是本工具最常查的内容；它不需要额外依赖，与其他数据在同一个数据库文件里。

**目录索引**：脚本为工作区的每个知识目录生成一个 `INDEX.md`，每个条目一行：编号、一句话摘要、路径，按类型分组；工作区根目录另有一个总索引。每个索引不超过 200 行，超出时按子目录拆分。索引只由脚本生成，不手写，每次知识变化后重新生成。

agent 查找信息分三级展开：先看索引或检索结果中的摘要，再按编号读取需要的条目正文，最后才读条目引用的原始材料。

## 16.5 查询接口

`retrieval` 组件对外提供四个操作，同时以命令行和本地 MCP 服务两种形式提供，支持 MCP 的工具走 MCP，不支持的走命令行：

| 操作 | 命令行 | 返回 |
|---|---|---|
| 检索 | `tightrein admin kb search <关键词> [--type] [--tags] [--status active] [--limit]` | 编号、摘要、路径、得分，不返回正文 |
| 取条目 | `tightrein admin kb get <编号>` | 条目全文与 frontmatter |
| 相关条目 | `tightrein admin kb related <编号>` | 通过 `related` 与 `supersededBy` 关联的条目 |
| 待复核 | `tightrein admin kb stale` | 过了复核日期、长期未被命中、相互矛盾的条目 |

检索默认只返回 `active` 的条目。每次 `get` 记录一次命中，命中次数用于 16.7 的淘汰判断。

## 16.6 为 agent 任务组装上下文

核心在调用执行器之前，先按任务类型预取一批相关条目，只把编号与摘要放进任务说明，agent 需要时再按编号读取正文：

| 任务 | 预取的条目 |
|---|---|
| 静态巡检的增量审查 | 与改动目录相关的缺陷模式(按缺陷模式的路由表与标签匹配) |
| 分诊 | 与问题所在接口、页面、文件相关的缺陷模式、已接受的取舍、分诊经验；同一路由或同一文件的历史问题与 Issue |
| 修复 | 与根因文件相关的修复经验、字段契约等项目知识；同一文件的历史修复报告 |

- 预取之外，agent 可以随时用 `admin kb search` 自行查找。
- 某一类条目在过滤后总量很小时(例如全部已接受的取舍不到几千 token)，直接把全文放进任务说明，不再分级展开。
- 上下文不是越多越好：输入越长，模型表现越差，而且下降是非线性的。因此默认只给摘要，按需展开。

## 16.7 写入、去重与淘汰

**写入时去重**：新增一条知识前，先用 `admin kb search` 找出相似条目，由 agent 判断是新增、更新已有条目、合并，还是不必写入，判断结果按 schema 返回，由核心执行。被新条目推翻的旧条目标为 `superseded` 并填写 `supersededBy`，不删除，历史仍可查询。

**定期复核**：`learn` 每周运行一次 `admin kb stale`，把以下条目列进周报：

- 过了 `reviewBy` 日期的条目
- 最近 90 天没有被命中的条目
- 内容相互矛盾的条目(由 agent 比对同类型、同标签的条目后给出)

用户在周报中确认处理方式：续期、合并、归档。归档的条目 `status` 改为 `archived`，默认不再被检索到。

## 16.8 检索评测

- 维护 50 到 100 条检索评测用例，放在工作区 `evals/retrieval/`。每条包括一个真实的查询(取自 agent 运行记录中的 `admin kb search`)与期望命中的条目编号。
- 指标：recall@5、recall@10、MRR。
- 每次修改索引、权重、标签或检索逻辑后运行一遍，指标下降的改动不采纳。
- 运行中发现的漏检(agent 没有查到、事后发现存在相关条目)补充为新的评测用例。

## 16.9 何时引入向量检索

同时满足以下两个条件时才引入：

1. 检索评测显示，同义表述或概念类查询的 recall@10 明显不达标；
2. 扩充标签与同义词后仍然不达标。

引入方式：在同一个 SQLite 文件中使用 `sqlite-vec` 存向量，与 FTS5 的结果用 RRF(倒数排名融合)合并；每个条目在生成向量前加上一段说明其来源与上下文的前缀。不单独部署向量数据库。

跨全部知识做主题归纳的需求(GraphRAG 擅长的场景)目前没有；条目之间的关系用 `related` 编号引用表达，通过 `admin kb related` 查询。

## 16.10 参考

- Claude Code 的检索方式：早期使用 RAG 与本地向量库，后改为 agent 按需探索(glob、grep、读文件)，效果更好，也没有索引过期、安全与可靠性方面的问题。
- Cursor 的语义检索实验：加入语义检索后问答准确率平均提高 12.5%，在 1000 个文件以上的仓库中收益更明显，grep 与语义检索结合效果最好。
- Sourcegraph Cody 放弃 embeddings，原因是代码需要发给第三方、索引运维负担重、超大规模下难以扩展。
- Aider 的仓库地图：用 tree-sitter 提取符号与引用，按 PageRank 排序，在 token 预算内生成仓库概览。
- Anthropic Contextual Retrieval：为每个分块加上下文前缀后，检索失败率降低 35%；再加 BM25 降低 49%；再加 rerank 降低 67%；知识库小于约 20 万 token 时可以直接全部放进提示，不需要 RAG。
- Anthropic 的上下文工程建议：保留轻量标识符(路径、编号、查询)，需要时再加载内容；子 agent 返回压缩摘要。
- Agent Skills 的渐进披露：启动时只加载名称与描述，触发时加载 `SKILL.md`，引用文件按需读取。
- Claude Code 的 memory：`MEMORY.md` 是一行一条的索引，只加载前 200 行或 25KB，主题文件按需读取。
- llms.txt：以 markdown 索引文件列出站点内容，标题、摘要与分组链接。
- SQLite FTS5：内置 `bm25()` 排序，可以为不同列设置权重。
- Chroma 的 context rot 研究：18 个模型在输入变长时表现都会下降，而且下降是非线性的。
- Self-Route 与 LaRA：长上下文与 RAG 没有通用的赢家，取决于模型、任务与长度；按问题路由可以兼顾质量与成本。
- GraphRAG：适合跨整个语料的全局归纳，具体事实查找用普通检索更好，建图成本高。
- Mem0：写入新事实前先检索相似条目，由模型判断新增、更新、删除或不写入；Zep/Graphiti：被推翻的事实标记失效而不删除。
- basic-memory：以 markdown 为数据来源、SQLite 为索引，全文与向量混合检索，以 MCP 工具形式提供。
- 检索评测的常见做法：收集真实查询并标注正确来源，计算 recall@k 与 MRR。
- sqlite-vec 与 FTS5 在同一个 SQLite 文件中做混合检索，用 RRF 合并结果。
