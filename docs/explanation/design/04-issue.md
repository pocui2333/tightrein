# 4. 提 Issue(本地)

## 4.1 职责

把分诊处理标签为「立即修」「排期修」的问题写成本地 Issue；用户自己提出的需求也可以直接建成 Issue(4.5)。Issue 是修复与跟踪的工作单：记录问题是什么、证据在哪、怎样算修好，后续的生成修复、验证和提 PR 都以它为依据。Issue 以本地为准；项目可以选择在 GitHub 上建镜像给用户阅读与讨论(4.11)，缺省只在本地。整体设计见 [redesign/04-issue.md](../redesign/04-issue.md)。

## 4.2 存放

- 每个 Issue 一个 markdown 文件，放在工作区的 `issues/`(`workspaces/demo/issues/`)下，文件名为 `<编号>-<简称>.md`，例如 `0007-material-query-500.md`。编号按创建顺序递增。
- Issue 文件是交接文档的 issue 类型([redesign/00-handoff-documents.md](../redesign/00-handoff-documents.md))：头信息加正文。文件是唯一的数据来源，数据库中的 `issues` 表只是索引，可以随时从文件重建。
- `~/Projects/tightrein/` 是个人 git 仓库，Issue 的每次修改都随提交留下历史。

## 4.3 头信息

| 字段 | 说明 |
|---|---|
| `kind`、`id`、`subject` | 交接文档的基础字段：类型为 `issue`，`id` 与 `subject` 都是 Issue 编号 |
| `status` | 状态，见 4.6 |
| `from`、`to` | 写出方为 `triage`(分诊生成)、`user`(用户需求)或 `fix`(修复计划拆分出的子任务)；接收方为 `fix` |
| `parent` | 上游：拆分出的子任务为父 Issue，分诊生成的为第一个关联问题，用户需求为空 |
| `created`、`updated`、`next` | 创建与更新时间；下一步命令，按状态生成 |
| `title` | 「[模块] 一句话说清现象与后果」，模块取顶层目录或功能名，长度上限 `thresholds.issue.titleMaxLength`；由取证输出的 `report.title` 给出，没有时为问题的机器标题 |
| `severity` | 分诊给出的严重度；用户需求的严重度由用户给出(缺省 P2) |
| `taskType`、`sizeTier`、`treatment` | 分诊给出的任务类型、规模档与处理标签(3.5)，决定修复的通道(5.2)；用户需求的类型由用户给出(缺省功能)，没有处理标签与规模档 |
| `source` | 来源：探针与档位、用户需求，或拆分自哪个 Issue |
| `origin`、`problems`、`rootCause`、`introducedBy`、`triageCommit`、`findings` | 程序字段：来源类别(`triage` 或 `manual`)、关联的问题 ID、根因位置(`文件:行号`)、引入提交、分诊时 `main` 的 commit、发现报告路径 |
| `branch`、`pr`、`runId` | 修复分支名、PR 链接、生成它的运行；分支与 PR 由后续模块回写 |
| `closeReason` | 关闭原因：完成为已修复；取消为修复未采纳、不修、重复、不是缺陷 |
| `phase` | 进行中的细分，以及完成后等待部署后确认(4.6)；只供程序推进 |
| `hold` | 为什么待决定：原因、环节、开始时间、详情；只出现在待决定的 Issue 上 |
| `github`、`dependsOn` | GitHub 镜像的编号与链接(4.11)；拆分出的子任务排在前面的那个 Issue |

旧版式的文件(`type: issue`，八种状态)照常可读，读取时按与迁移 009 相同的映射换算状态；`issue rerender` 写回即为新版式。

## 4.4 正文

正文按交接文档的基础小节组织：结论、内容、需要决定、下一步、引用、历史。「内容」下为问题、影响、复现、原因、范围、注意事项、验收标准、修复方向八个小节；验收标准固定三条在前：复现测试修复前失败、修复后通过，现有测试全部通过，必须保持不变的行为。各小节的写法与依据见 [redesign/04-issue.md](../redesign/04-issue.md) 第 6 节，内容来源见 architecture/06 10.3。正文与标题按 `project.language`(缺省 en)书写，小节标题有 zh、en、ja 三套。

正文由分诊的结构化结论生成，缺少的字段显示「—」，不丢节。代码位置一律写相对仓库根的完整路径；只写了文件名的由工具按代码快照补全，补不全时不建 Issue，交回重新分诊。用 `issue rerender` 可按当前版式重写已有 Issue(不调用模型，缺的字段仍为「—」)。

## 4.5 创建规则

- **只为立即修、排期修建 Issue**：处理标签为「观察」的问题暂不修，再次出现或严重度升级后恢复并重新分诊，仍判为观察的升为排期修并建 Issue；「不修」的按已接受的取舍关闭，不建 Issue。
- **一个根因一个 Issue**：分诊交来的问题如果与某个未关闭 Issue 的根因位置相同，把问题追加到该 Issue 的 `problems` 中，不新建。
- **自动创建，人工放行**：Issue 只写在本地、可以随时修改或删除，因此由工具自动创建，不需要事先确认。新建的 Issue 状态为「待决定」，用户放行后才进入修复流程；开启自主放行(4.12)且满足规则的立即放行为「待修」。
- **P0 立即通知**：P0 问题创建 Issue 后立即发本机通知，不等运行摘要。
- **用户需求**：`issue create --manual --title <标题> (--body <文本> | --body-file <文件>)` 直接新建 Issue，`origin` 为 `manual`，不关联问题与信号，不写运行记录与交接文档。用户亲自提出的需求免审阅，创建即为「待修」；之后照常 `issue approve`(不改状态，只申请建修复分支)进入修复；开启自主决定(4.12)的项目创建即放行并申请建分支。修复计划超出改动量上限而拆分出的后续子任务也以这种 Issue 建立，`parent` 为父 Issue、`dependsOn` 为前一个子任务，前一个子任务完成后才可开始(design 5.5)。正文的「问题」为用户原文，验收标准为原文中的验收标准(没有时写说明)加固定三条，其余小节写「—」；修复的勘察与计划以正文为需求。用户需求没有复现检查(5.6、6.x)，不起草缺陷模式，也不能从分诊重来。

## 4.6 状态

| 状态 | 含义 | 由谁转入 |
|---|---|---|
| 待决定(`needs-decision`) | 等待用户决定：新建的分诊 Issue 等待放行，或修复、验证停下需要用户处理(带 `hold`) | 工具创建；修复或验证停下 |
| 待修(`todo`) | 可以开始修复；用户需求创建即为此状态 | 用户放行或自主放行；合并前验证失败、部署后确认失败、重新打开 |
| 进行中(`in-progress`) | 修复、合并前验证与提交 | 生成修复模块(`fix start`) |
| 待合并(`pending-merge`) | PR 已创建，等待合并 | 提 PR 的环节 |
| 完成(`done`) | PR 已合并，关闭原因为已修复 | PR 合并 |
| 取消(`cancelled`) | 修复未采纳、不修、重复或不是缺陷 | 修复未采纳由工具根据 PR 结果判定，其余由用户关闭 |

- **进行中的细分**记在头信息的 `phase`：`fix`(修复)、`verify`(合并前验证)、`submit`(提交)；完成后等待部署后确认为 `deploy-check`。`phase` 只供程序推进(下一步、无人值守、跟踪)，不作为状态显示，不进 GitHub 标签；修复第 0 到 9 步的进度记在修复的进度文档中。
- **完成**：PR 合并即为完成，等待部署后确认；部署后确认通过才同步关联问题、回填分诊结果并清空 `phase`，失败时回到「待修」。
- **取消**：PR 关闭且未合并为修复未采纳；不修、重复、不是缺陷由用户关闭并写明原因。「不是缺陷」会回填到 3.10 的效果反馈中。
- 用户在「待决定」时可以修改正文，例如补充复现步骤、调整修复方向，修改后再放行。
- **`hold`** 不是状态，只出现在待决定的 Issue 上，说明为什么待决定：修复中评审或计划重出超过上限、写不出复现测试、连续 2 次合并前验证失败、根因在设计本身、无人值守修复停下、用户选择转为与代码作者讨论时，Issue 转为待决定并记下原因。带 `hold` 的 Issue 不会被自动推进，用户以 `fix start --force` 确认继续后清除。
- 修复过程中 Issue 可能回退：复现测试在基准版本上就通过(5.6)时从「进行中」回到「待决定」并重新分诊；合并前验证失败时回到「待修」；修复分支合并了 `main` 后回到合并前验证；部署后确认失败时从「完成」回到「待修」。转换表见 architecture/01 2.3。

## 4.7 与问题状态同步

| 事件 | 处理 |
|---|---|
| 关联的问题回归 | 完成或取消的 Issue 重新打开为「待修」(等待部署后确认的按部署后确认失败处理)，历史中记录回归时的 commit |
| Issue 部署后确认通过 | 关联的问题按已修复同步，分诊结论回填为正确 |
| Issue 以「不修」取消 | 关联的问题转为「已忽略」，恢复条件为严重度升级或出现在新版本中 |
| Issue 以「修复未采纳」取消 | 与「不修」相同 |
| Issue 以「不是缺陷」取消 | 关联的问题判为误报，按 2.9 生成抑制规则 |
| Issue 以「重复」取消 | 关联的问题并入被重复的那个 Issue |

## 4.8 命令

| 命令 | 作用 |
|---|---|
| `issue list [--status <状态>] [--severity <等级>]` | 列出 Issue，默认按严重度与创建时间排序 |
| `issue show <编号>` | 查看 Issue 全文与关联问题的最新情况 |
| `issue edit <编号>` | 用编辑器打开 Issue 文件 |
| `issue create` | 为分诊判为提 Issue 的问题创建或追加 Issue，由编排自动执行 |
| `issue create --manual --title <标题> (--body <文本> \| --body-file <文件>) [--severity <等级>]` | 新建用户需求的 Issue(4.5)，状态为「待修」 |
| `issue sync` | 执行 4.7 的同步与待决定超时提醒；有 GitHub 镜像时再对齐镜像并列出未同步项(4.11) |
| `issue approve <编号>` | 放行：状态改为「待修」，随后当场生成建修复分支与 worktree 的待确认操作交用户确认(5.3)。这是一个组合命令：`issue` 模块只做状态转换，建分支由 `fix prepare` 向 `vcs` 申请；用户拒绝建分支时 Issue 仍为「待修」，之后执行 `fix prepare <编号>` 再次申请 |
| `issue close <编号> --reason <原因> [--note <说明>] [--duplicate-of <编号>]` | 关闭为取消；原因只能是不修、重复、不是缺陷，重复时必须给出被重复的 Issue；已修复与修复未采纳只由工具根据 PR 结果写入 |
| `issue reopen <编号>` | 重新打开为「待修」 |
| `issue rerender [<编号>...]` | 按当前版式重写 Issue 正文(4.4)，旧版式转为新版式 |
| `issue reindex` | 从 Issue 文件重建 `issues` 表 |

所有命令对 Issue 的修改都在「历史」一节追加一行记录。

## 4.9 运行摘要

每次运行摘要中列出：新建的 Issue、状态变化的 Issue、待决定的 Issue 数量，以及等待放行超过 3 个工作日的 Issue。

## 4.10 参考

- Backlog.md、git-issues：把 Issue 以 markdown 加 YAML frontmatter 的形式存放在仓库中，不需要服务端和账号，便于人与 AI agent 共同读写。本工具的 Issue 格式采用同样的思路。

## 4.11 GitHub 镜像

按项目选择 Issue 去向：`project.yaml` 的 `issues.tracker` 缺省为 `local`，只在本地(团队不在 GitHub 上提 Issue 的项目沿用)；设为 `github` 时，每个未关闭的本地 Issue 在 GitHub 上有一个镜像 Issue，给用户阅读与讨论。

- **字段归属**：开关状态以 GitHub 为准，标题、正文、标签与父子、阻塞关系以本地为准，每次对齐按本地覆盖。用户在 GitHub 上关闭，本地按「用户关闭」取消(原因为不修)；在 GitHub 上重新打开，本地重新打开为「待修」。PR 描述带 `Closes #<编号>`，PR 合并时 GitHub 自动关闭镜像，这不算用户关闭。正文编辑与评论不同步回本地。
- **正文**：与本地相同(去掉「历史」，经脱敏)，代码位置是指向取证 commit 的永久链接，「引用」中的完整证据折叠；创建时写入，`issue rerender` 时更新。进度由标签与关键节点评论(放行、修复计划确认、PR 创建、PR 合并、关闭)体现。
- **标签**：每个 Issue 一个状态标签 `<前缀><状态>`(例如 `tightrein:needs-decision`)加一个类型标签 `<前缀>type:<任务类型>`，缺失时自动建立。GitHub 的 Issue 类型只在组织级别可用，因此用标签表示。
- **子 Issue 与阻塞**：拆分出的子任务用 GitHub 原生的子 Issue(父 Issue)与阻塞关系(前一个子任务)表示，网页上直接可见层级与先后顺序；对方还没有镜像时，之后的对齐补上。
- **只用私有仓库**：缺省只允许私有仓库(`issues.github.privateOnly`)，公开仓库时拒绝同步并说明原因，缺陷与安全发现不应公开。仓库缺省取项目 origin 远程。
- **确认**：镜像写入属于对外写操作，缺省逐次确认(运行摘要中列出待确认的镜像操作)；项目可以在关卡表中把 `gates.mirror-writes` 设为 `auto`，声明本项目 Issue 镜像无需逐次确认，只影响镜像，不影响提交、推送、提 PR 等确认。
- **失败不阻断**：GitHub 调用失败不影响本地流程，下一次运行重试；`issue sync` 与运行摘要列出未同步的项。

## 4.12 自主放行

个人项目可以把关卡 `gates.issue-approve` 设为 `auto`(缺省 `user`，示例项目不开；关卡表见 architecture/09 3.8)：简单的 Issue 不必等用户放行，无法自行决定的仍交用户。

- **何时判断**：`issue create` 新建 Issue 时；追加到已有 Issue 的不判断。用户直接提出的需求创建即为「待修」，照常视为已放行。
- **自动放行的条件**(全部满足)：关联问题都有分诊结论；没有「需要先与代码作者讨论」的标注；没有需用户定夺的标记(根因在设计本身、数据结构或存量数据、公共实现或接口契约)；影响类别不是权限、数据归属(`autonomy.approve.impactKinds`)；任务复杂度为低(13.3，`autonomy.approve.maxComplexity`)；严重度不在需用户决定的列表中(`autonomy.approve.severities`，缺省空)。
- **满足时**：Issue 放行为「待修」，「历史」写「自动放行：满足 …」，随后照常申请建修复分支(5.3)。
- **不满足时**：留在「待决定」，「历史」与 GitHub 镜像评论写「需要用户决定：…」，由用户 `issue approve` 或关闭。
- 每次自动决定都记事件，运行摘要「自动决定」一节分别列出自动放行与需要用户决定的 Issue。
