# 8. 观测学习

当前设计见 [redesign/08-learn.md](../redesign/08-learn.md)，本章是它的展开。

## 8.1 职责

学习模块记录每次运行的结果，把经验与修好的缺陷沉淀下来，并为系统与用户提供决策依据。它不训练模型，也不自动修改自身：
凡是改提示、改配置的调整，都以建议进收件箱，由用户批准后自己修改。

| 功能 | 做法 |
|---|---|
| 环节效益统计 | 程序记录每次模型调用的工具、模型、费用与结果；按通道、按模型统计一次通过率、每个修复的费用、被撤销的比例(8.3) |
| 周报 | 程序生成的 result 类型交接文档(8.4) |
| 经验总结 | 只在出问题时写，带来源与复核日期，长期未被使用的自动归档(8.5) |
| 缺陷变规则 | 修好一个缺陷后生成一条 Semgrep 规则，用原补丁验证通过才收入规则库(8.6) |
| 运行即评测 | 修复部署后确认通过时，程序把这次修复存为评测用例(8.7) |
| 知识库与检索 | 全文检索与 MCP 接口(第 16 章) |
| 链路健康 | 程序检查各环节是否正常运行(8.8) |
| 自我改进 | 只做建议，附评测对比，用户批准后才生效(第 14 章) |

前面各章已经埋好了数据：归并的 `runs` 与 `problems`、分诊的实际结果(3.10)、Issue 的状态历史(第 4 章)、修复与验证的交接文档、
PR 与部署记录(第 7 章)、各模块调用执行器之后登记的环节效益(`stage_yield`)。本章只汇总、分析和沉淀，不重复采集。

## 8.2 修复的长期跟踪

- 工作区 `regressions/` 下的复现检查随部署后确认与对应来源的巡检一起执行。
- 已修复的 Issue 对应的复现检查失败时，产出一条回归信号，归并模块把关联问题判为「回归」，Issue 按 4.7 重新打开。
- 同一个 Issue 回归两次及以上的，在周报中单独列出：说明局部修复没有根治，需要考虑设计层面的问题。

## 8.3 指标

评分只作衡量手段(第 12 章)：以确定性的结果为主，给系统与用户看，不放进模型的提示。

| 环节 | 指标 | 计算方式 | 用于决定 |
|---|---|---|---|
| 发现 | 新发现问题数、接口覆盖率、噪声占比 | 归并的状态与运行的覆盖范围 | 采集配置是否合适 |
| 分诊 | 分诊准确率 | 判为成立的，复现测试是否确实在修复前失败(修复前复现不了回填为误判成立)；判为误报的，之后是否再出现 | 证伪复核是否扩大范围 |
| 分诊 | 人工队列积压 | 处于人工队列的问题数与最长等待工作日 | — |
| 修复 | 一次通过率(按通道、按模型) | 每个 Issue 本周第一份带轮次的修复交接文档中，第一轮复现测试与项目检查即通过 | 写代码的模型是否够用，是否升级 |
| 修复 | 每个修复的费用(按通道) | 以已修复关闭的 Issue 在修复、验证、发布环节全部调用的费用之和的平均 | 预算与通道划分 |
| 修复 | 各段耗时、验证一次通过率、改动量分布 | Issue 历史、验证与修复的交接文档 | 链路中最慢的一段 |
| 结果 | 已修复数、回归率、PR 被拒率 | Issue 与 PR 记录 | — |
| 结果 | 被撤销的比例(按通道) | 回看期内以已修复关闭的 Issue 中，撤销 PR 已确认或已执行的比例 | 各通道的真实质量 |
| 用户 | 用户纠正次数 | 驳回修复计划、关闭 Issue、确认撤销 PR、改判分诊结论的次数 | 自主决定的门槛是否收紧 |
| 成本 | token、费用与耗时 | 事件日志与运行记录 | — |

「回归率」与「被撤销的比例」对应 DORA 指标中的变更失败率与返工率。一次通过率的模型维度取同一运行中写代码的调用
(`fix-executor`、`fix-session`)在环节效益中记下的模型；旧记录没有模型时为 `unknown`。

## 8.4 周报

每周第一个工作日由程序生成 `data/reports/weekly-<周一>.md`，为 result 类型的交接文档，并发本机通知：

| 小节 | 内容 |
|---|---|
| 结论 | 本周新发现、已修复、回归的问题数(与上周对比)，一次通过率，需要处理的事项与待处理的建议数 |
| 做了什么 | 统计周期与生成时间(绝对日期并注明时区) |
| 产出 | 指标表(本周、上周、趋势、样本数)、环节效益表、本周的缺陷变规则结果(收入规则库的规则与未收录的原因)、经验清理、待处理的建议 |
| 证据 | 链路健康与第三方 skill 核实，逐项结果写在数据块 `checks` 中 |
| 偏离与原因 | 统计出错的项 |
| 需要决定 | 待处理的学习建议，每条带推荐与理由 |
| 下一步 | 需要处理的事项与命令：等待放行与待合并的 Issue 和 PR、人工队列、即将到期的抑制规则、自动判为误报的问题(供抽查)、回归两次及以上的 Issue、需要手写的经验 |

## 8.5 经验总结

只在出问题时写，不从正常完成的运行中取材料：

| 出问题的来源 | 写成 |
|---|---|
| 分诊误判(误判为成立、误判为不成立、用户改判) | 分诊经验 `knowledge/triage-lesson/` |
| 评审驳回：PR 上要求修改的评审、修复评审不通过的轮次 | 修复经验 `knowledge/fix-lesson/` |
| 修复失败(转人工) | 修复经验 |
| 被撤销(撤销 PR) | 修复经验 |
| 用户纠正：驳回修复计划、关闭 Issue | 修复经验 |

- 经验由 `lesson-writer` 撰写，经写入去重(16.7)后直接写入；正文末尾由程序加「来源」一节(类型、对象、运行)，复核日期为写入日加
  `thresholds.learn.lessonReviewDays` 天。
- **自动清理**：经验类条目过了复核日期且最近 `retrieval.unusedDays` 天没有被命中的自动归档(可恢复)，仍被命中的自动续期。
  缺陷模式、取舍、约定等其他类型过期或长期未命中时生成复核建议，由用户决定；同类条目的矛盾与重复也生成复核建议。
- 经验类复用有效(Reflexion)，但需要清理机制，避免记忆积累噪音。

## 8.6 缺陷变规则

修好一个缺陷后，`rule-writer` 写一条 Semgrep 规则，程序用原补丁验证(参照 KNighter)：

1. 修复前的代码(改动文件在基准 commit 上的内容)至少命中一处；
2. 修复后的代码(合并提交上的内容)不命中；
3. 在只读 worktree 全仓库运行，命中数不超过 `thresholds.learn.rules.maxRepoHits`(误报的上限，不逐条区分真实同类与误报)。

三项都通过的规则写进工作区 `rules/<Issue>-<简称>.yaml`(头部注释写来源与验证数字)。静态巡检单独运行规则库，命中直接成为信号，
不经审查与取证，由分诊照常处理；之后同类问题由程序确定性地检测。规则表达不了或验证不通过的，不收录并写明原因，缺陷模式的描述
作为 `defect-pattern` 条目写入知识库，由静态巡检全量扫描时的同类查找(`variant-scan`)按描述查找。每个 Issue 只处理一次。

## 8.7 运行即评测

一个 Issue 的修复合并且部署后确认通过时，程序把这次运行保存为评测用例 `data/eval/cases/<Issue 编号>.json`：Issue 正文、
修复前的提交、登记的复现测试、最终补丁，另存该 Issue 的 issue 环节交接文档作为评测输入。评测 fix 时这些真实用例与 `evals/`
中封存的用例一起使用；自我改进建议的评测以它们为数据(14.4)。

## 8.8 链路健康检查

每次运行结束和生成周报时检查：

| 检查 | 判定 | 处理 |
|---|---|---|
| 漏跑 | 按计划应该运行而没有记录，例如电脑休眠错过了定时 | 周报列出；连续漏跑 2 次时发通知 |
| 异常退出 | 记录了开始时间而没有结束时间，或者以错误结束 | 立即通知，附日志路径 |
| 长期没有产出 | 某个来源连续 10 次运行没有产出任何信号 | 周报提示检查，可能已失效，例如登录态过期 |
| 部署检测停滞 | 有新的部署成功记录，而部署后浅跑没有触发 | 立即通知 |
| 测试账号异常 | 登录失败的角色 | 立即通知 |
| 数据目录膨胀 | `data/` 超过设定大小 | 周报提示，按保留期清理 |

## 8.9 学习建议

学习只产出建议，`learn accept` 只记录用户的决定(知识复核除外，按 `--action` 续期、合并或归档条目)，不修改任何配置、提示或代码。
待处理的建议进收件箱与周报的「需要决定」。

| 类型 | 来源 |
|---|---|
| 采集配置 `probe-config` | 同一检查本周被判误报或作废集中 |
| 覆盖缺口 `coverage-gap` | 接口描述中连续多周没有被覆盖的接口 |
| 知识复核 `knowledge-review` | 非经验类条目过期或长期未命中、矛盾与重复 |
| 控制措施 `control` | 分数驱动的控制(12.3)，附决定文档 |
| 改进建议 `improvement` | 自我改进(第 14 章)，附决定文档与评测对比 |

## 8.10 参考

- DORA 软件交付指标：变更失败率衡量需要修补或回滚的变更占比，2024 年起以返工率补充衡量返工量。
- Reflexion：以文字形式保存的经验对后续任务有效；经验需要来源与清理，否则噪音会累积。
- KNighter：从修好的缺陷生成静态检查器，用原补丁验证(修复前命中、修复后不命中)，并控制全仓库的误报。
- Sentry 内部的自动化调试流程：以 PR 处理率与 48 小时内响应率衡量效果；未合并就关闭的 PR 往往是工程师选择了更彻底的修复。
