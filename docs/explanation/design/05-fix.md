# 5. 生成修复

## 5.1 职责

把用户放行的 Issue 变成代码改动：在独立的工作区和修复分支上完成修改，通过项目要求的检查，停在「改动都在工作区、未提交」。提交、推送和提 PR 属于后续环节。

## 5.2 修复的组成

修复按「任务类型 × 规模档」分流到三条通道，再按第 0 到 9 步推进；通道、步骤与模型选择的依据见 [redesign/05-fix.md](../redesign/05-fix.md)。

| 通道 | 适用(缺省流程表 `fix.lanes`) | 经过的步骤 |
|---|---|---|
| A 快速 | 微档、小档，且类型不是安全、数据、依赖 | 分流、准备、写复现测试、写代码、收集结果、轻量评审、完成；计划由核心按 Issue 生成 |
| B 标准 | 中档；或安全、数据、依赖类的微、小、中档 | 在 A 的基础上按需勘察、出计划、确认计划；评审为轻量，高风险另加深度 |
| C 大任务 | 大档 | 出整体方案交用户确认，再拆成子 Issue，各子 Issue 从第 0 步开始按 A 或 B 处理 |
| 超限 | 超出大档 | 不接：Issue 转待决定，生成建议如何拆分需求的决定请求 |

下列角色经 agent 执行器运行，角色说明在 `skills/fix/references/roles/` 下，各角色的结构化输出先写自由分析(`analysis`)，所用模型档见 9.6：

| 角色 | 职责 | 何时运行 | 模型档 |
|---|---|---|---|
| `fix-scout` | 只读勘察：根因位置、联动方(调用者与依赖其输出的地方)、可复用的现成实现、复现线索 | B 通道，Issue 缺根因位置或范围，或类型在 `fix.scout.taskTypes`(缺省安全、数据)中 | 轻量档 |
| `fix-planner` | 给出修复计划：只取根治问题的最小改动，写清文件与步骤、验收标准对照、不做什么、需要用户拍板的点、预估改动量；对照受保护文件清单(11.2)与三类需用户定夺的问题(3.2) | B、C 通道 | 强档 |
| `frontend-designer` | 给出前端设计说明：页面与组件结构、布局与信息层级、交互与加载、空、出错状态、样式取值(优先既有设计变量与组件)、手机端适配、文案；`fix-executor` 按它实现 | 计划预估改动的文件中有前端文件时 | 强档 |
| `fix-executor` | 同一会话的两轮：第一轮只写表达验收标准的测试，第二轮按 Issue 或计划修改代码 | A、B 通道 | 强档 |
| `repro-writer` | 在与写代码不同的会话中独立写复现测试 | 类型在 `fix.repro.independentTypes`(缺省安全、数据)中 | 强档 |
| `fix-reviewer` | 评审：A 轻量；B 轻量，高风险另加深度(5.8) | 第 7 步的检查全部通过后 | 轻量评审为标准档，深度评审为强档 |

**流程**

| 步 | 做什么 |
|---|---|
| 0 分流 | 类型、规模档与处理标签取 Issue 头信息(没有时取关联问题的分诊结论)，查流程表定通道；超限转待决定。产出进度文档，之后每一步更新它 |
| 1 准备 | 建修复分支与 worktree(5.3)，在基准版本上全量运行项目检查命令自检；不通过说明是配置或环境问题，Issue 转为待决定并报配置错误，不进入修复 |
| 2 勘察 | B 通道按需运行 `fix-scout`，产出勘察结果并追加到 Issue 的引用中 |
| 3 出计划 | B、C 由 `fix-planner` 出计划；核心按计划预估重评规模档(只升不降，升为大档转 C，超限转待决定)，超出单个 PR 上限(5.5)时要求拆分，并按 5.8 标出风险；含前端文件时 `frontend-designer` 出前端设计说明。A 由核心按 Issue 生成计划，文件取分诊预估 |
| 4 确认计划 | A 自动确认；B 满足自主决定规则(5.4)时自动确认，否则交用户；C 一律交用户，确认后拆成子 Issue，本 Issue 做第一个子任务 |
| 5 写复现测试 | 见 5.6；文档与配置类跳过 |
| 6 写代码 | `fix-executor` 第二轮(续接第 5 步的会话；独立写测试时新开会话)；核心检查改动不超出当前档与单个 PR 上限、不改受保护文件、不删改已有测试、不加跳过标记。A 通道超档转 B，已写的测试保留；B 通道超档但在单个 PR 上限内记录升档后继续 |
| 7 收集结果 | 运行复现测试(须通过)、全部项目检查(全量)与相关的其他复现检查，统计 diff，产出结果文档；不通过回第 6 步 |
| 8 评审 | 输入 Issue、计划、diff 与第 7 步的结果文档；A 轻量(实际改动为微档且检查都通过时跳过，`fix.review.skipMicro`)，B 轻量，高风险另加深度；有阻断项回第 6 步 |
| 9 完成 | 核对产出(5.7)，进度文档标记完成，Issue 进入合并前验证 |

第 6 到 8 步的修改轮数上限为 `thresholds.fix.reviewRounds`(缺省 3)，超过时转待决定，写明卡点。拒绝计划、规范要求用户确认(新增依赖、删除文件、
改动受保护文件)或根因在设计本身(5.5)时停下交用户。

**评审只报告两类问题**

| 类别 | 包括 |
|---|---|
| 影响正确性 | 根因没有修掉；破坏了已有调用方或其他入口；只针对复现测试的输入写死的特殊处理；新增的错误路径(吞掉异常、把内部异常信息返回给调用方、失败后留下中间状态) |
| 不满足需求 | Issue 的验收标准没有达成；缩减了需求 |

风格、命名、写法偏好不报；没有具体触发条件的假想风险不报。每个问题必须给出 `文件路径:行号` 与触发条件，缺少任一项的由核心丢弃，不计为不通过。评审看不到 `fix-executor` 的自述与会话记录。

**原则**

- 输入是 Issue 与发现报告，不再做需求拆解与提问；分诊已完成定位，A 通道的 Issue 本身就是计划。
- 给各角色的是任务、路径和已核实的事实；`fix-executor` 拿到的是已确认的计划，照计划执行。
- 最小修复(5.5)与先写复现测试后修复(5.6)。
- 各步产出交接文档：进度(`progress.md`)、任务(`task.md`)、勘察(`scout.md`)、计划(`plan.md`)、结果(`result.md`)、评审(`review-<轮>-<模式>.md`)、决定请求(`decision.md`)，存放在 `data/fixes/<Issue 编号>/`。
- 修复途中顺带发现的问题写进结果文档的「任务外发现」一节，由 1.6.5 转成信号。
- 能由代码判定的都由确定性检查判定，评审只判断代码判定不了的部分；角色说明中不要求 agent 交付前再验证一遍，也不要求用子 agent 复核。

## 5.3 工作区与分支

- **分支名**：按项目约定生成(7.2 的「格式与约定」)，通用格式为 `<类型>/<Issue 编号>-<简称>`，类型由任务类型映射，简称取自 Issue 文件名。项目要求个人前缀时(`git.personalPrefix` 或项目的分支模板)在前面加个人前缀，前缀由用户在本工具配置中设定，不使用 AI 或工具名称。
- **工作区**：每个 Issue 一个可写 worktree，放在工作区的 `worktrees/fix-<Issue 编号>/`(`workspaces/demo/worktrees/fix-<Issue 编号>/`)，从最新的 `origin/main` 创建修复分支，不纳入本工具仓库的版本管理。创建后按 `project.yaml` 的 `git.worktreeLinks` 从项目主工作区链接 `.claude/` 等目录，再执行 `checks.prepare` 中的准备命令(例如安装前端依赖)。静态巡检与分诊使用的只读 worktree(`worktrees/readonly/`)与之分开。
- **git 写操作的确认**：建分支和建 worktree 属于 git 写操作。`issue approve` 时由 `fix prepare` 生成待确认操作，列出将要执行的命令、分支名和影响，用户确认后才执行；用户当时拒绝的，之后可以再执行 `fix prepare <Issue 编号>`。此后的提交与推送在后续环节中逐次确认。项目在关卡表中把 `gates.release-writes` 设为 `auto` 时建分支与之后的提交、推送、提 PR 直接执行(7.10)。

## 5.4 运行方式

缺省在前台修复会话中推进(B、C 通道的计划需要用户确认)；关卡 `gates.fix-session` 为 `auto` 时由编排以非交互任务无人值守推进，需要用户时停在关口。修复拆成一组子命令，每个子命令都是独立的核心调用，各角色在子命令内部经 agent 执行器以无人值守方式运行，结果写入存储：

| 命令 | 作用 |
|---|---|
| `fix prepare <Issue 编号>` | 生成建修复分支与 worktree 的待确认操作；由 `issue approve` 组合调用，也可单独执行 |
| `fix start <Issue 编号> [--here]` | 检查 Issue 状态为「待修」(或从「进行中」「待合并」重新进入；带 `hold` 的「待决定」需加 `--force` 确认)，状态改为「进行中」，在该 Issue 的 worktree 中启动 `project.yaml` 指定工具的交互会话，加载本工具的 `fix` skill，把 Issue 文件路径、发现报告路径作为首条输入；`--here` 不启动新会话，在当前 agent 会话中按 `fix` skill 继续 |
| `fix plan <Issue 编号> [--note <说明>] [--accept-design]` | 第 0 到 4 步：分流、建立确定性来源的复现检查、按需勘察、出计划，生成计划确认(或自动确认)；说明与决定记录下来，之后持续交给各修复角色 |
| `fix confirm <Issue 编号> [--reject] [--note <说明>]` | 确认或拒绝修复计划；拒绝时带 `--note` 即按说明重出计划 |
| `fix apply <Issue 编号> [--review-only]` | 第 5 到 8 步：写复现测试并在基准版本上验证、写代码、收集结果、评审与修改循环 |
| `fix done <Issue 编号>` | 第 9 步：核对产出(5.7)，Issue 进入合并前验证 |
| `fix abandon <Issue 编号> --reason <原因>` | 停止本次修复：Issue 转为「待决定」(4.6 的 `hold`)，改动保留在 worktree 中 |
| `fix cleanup <Issue 编号>` | 收尾清理(7.9) |

一次修复的顺序：

1. `fix start` 打开交互会话。会话本身只读，不直接编辑代码，只调用上表的子命令与只读命令，每一步之后向用户转述结果。
2. 会话中执行 `fix plan`；计划需要用户确认时停下，用户表态后由 skill 执行 `fix confirm`。
3. `fix apply` 写复现测试、写代码、收集结果并完成评审与修改循环，改动留在 worktree 中。
4. `fix done` 收集本次修复的产出，Issue 进入合并前验证。会话结束。

不进入 agent 会话时，也可以在终端执行 `tightrein continue <Issue 编号> --until verify`，由编排按同样的顺序调用这些子命令，计划确认在终端中进行。会话中断后再次 `fix start`，从已完成的步骤之后继续。

**自动确认计划**：A 通道的计划由核心生成，自动确认；C 通道一律交用户。关卡 `gates.plan-confirm` 为 `auto`(4.12，缺省 `user`)时，B 通道的计划满足以下全部条件即自动确认，等同 `fix confirm`，会话直接进入 `fix apply`：没有待定问题；三类需用户定夺的标记都未命中；不改动受保护文件、不改动权限与密钥配置(必须交用户)、没有迁移、不新增依赖、不删除文件；预估改动不超过 3 个文件、100 行(`thresholds.autonomy.planMaxFiles`、`planMaxLines`，不大于单个 PR 上限)；前端设计说明(如有)与计划没有冲突。任一条不满足就照常停下交用户，「历史」与 GitHub 镜像评论写「修复计划需要用户确认：…」。

**无人值守修复**：关卡 `gates.fix-session` 为 `auto` 的项目，Issue 放行后由 loop(定时 `run` 与 `continue`)直接推进，不启动交互会话：依次执行 `fix plan`、自动确认、`fix apply`、`fix done`，之后照常合并前验证与发布。计划需要用户确认时停在确认关口；其他失败(边界违规、检查不通过且修正用尽等)转为「待决定」，GitHub 镜像的状态标签随之为 `needs-decision` 并在评论中写明原因。`gates.issue-approve` 为 `auto` 时用户需求的 Issue 创建即放行并建分支。同时修复的 Issue 不超过 `loop.maxActiveFixes`(缺省 1)，立即修先于排期修；同一对象反复失败时熔断转待决定(architecture/09 3.10)。

## 5.5 修复范围

- 只修 Issue 描述的问题。修复途中发现的其他问题，按项目规则只写进汇报；本工具把它们作为新的问题登记，走正常的分诊流程，不混进本次修复。
- 修复的是其他开发人员写的代码，只做根治问题所需的最小改动，保持原有写法和结构，便于对方审阅：
  - 不拆分文件，不抽取公共实现，不顺手重构、改名或调整格式。
  - 不删除与本问题无关的代码，即使它看起来是死代码。
- **不过度设计**：写进 `fix-planner`、`fix-executor` 的角色说明与共同的修复规则：
  - 只做计划要求的改动，不为假想的需求增加抽象、参数、配置项或开关。
  - 只在系统边界(接口入参、外部输入、外部服务返回)做校验，内部调用之间不重复校验。
  - 测试只写第 5 步表达验收标准的那一个(5.6)，写代码时不删改已有测试、不加跳过标记。
- **规模与单个 PR 上限**：规模档决定通道(5.2，门槛见 13.1)；单个 PR 改动文件数不超过 10 个、变更行数不超过 500 行，都不含测试文件(配置项 `thresholds.change.maxFiles`、`thresholds.change.maxLines`，缺省与中档一致，B 通道的中档任务不必拆分)。依据：Google 的小 CL 实践、Cisco 的评审研究、DORA 的小批量交付，以及 stacked PR 每层单独成立的做法。
  - 计划预估超出单个 PR 上限，或重评为大档时，修复计划改为拆分：一组有先后顺序的子任务，每个只做一件事、单独合入也成立，各自在上限内；第一个子任务满足本 Issue 的验收标准，当前 Issue 只做它，其余在计划确认后生成为排队的后续 Issue(带类型与档)，前一个完成(PR 已合并)后才开始下一个。
  - 实施后实际改动超出当前档时，A 通道转 B 通道重出计划；超出单个 PR 上限时交回修改，修改轮数用尽仍超出时转待决定。
  - 新增模块或新目录由用户决定。
- 根因在设计本身、局部修补无法根治时，修复会停下交给用户。此时 Issue 转为「待决定」(4.6 的 `hold`)，历史中记录原因，由用户决定是找代码作者讨论，还是扩大修复范围后重新开始。

## 5.6 修复前先复现

- **复现测试(第 5 步)**：`fix-executor` 第一轮只写一个表达验收标准的测试(安全、数据类由 `repro-writer` 在另一会话中独立写)：缺陷类为复现测试，新功能类按验收标准写测试，重构类为固定现有行为的表征测试；文档与配置类跳过。核心检查只改了 `testPaths` 中的文件、运行命令以允许的前缀开头并选中了该测试，然后在基准版本上运行：重构类须通过，其余须失败。缺陷类在基准版本上就通过，说明问题不成立，结果为 `not-reproduced`，Issue 退回分诊；写不出合格测试时转待决定。合格的测试登记为本 Issue 的测试类复现检查(`repro.json` 记录测试与基准结果)，随修复由发布提交；修复后第 7 步须通过。
- **确定性来源的复现检查**：api-fuzz、e2e、static 的问题在第 0 步由核心直接生成复现检查(API 问题是一条可以重放的请求加上期望的响应，页面问题是一条 Playwright 用例，静态问题是能命中该缺陷模式的检查规则)，供部署后确认与回归。问题是否真实存在由第 5 步的复现测试(`repro.json`)确认，验证模块不另做修复前复现。
- 用户需求的 Issue(4.5，没有关联问题)类型取 `issue create --manual --type`(缺省功能)，档未知按中档查流程表进入 B 通道，由计划重评规模档；第 5 步按验收标准写测试。
- 复现检查由核心写入工作区的 `regressions/<Issue 编号>/`(`workspaces/demo/regressions/<Issue 编号>/`)，任何 agent 都不能写这个目录；它不写进项目仓库(测试类的测试文件另放进修复分支)，也不在修复完成后删除，每条检查的哈希登记在数据库中，被改动时直接报错。之后的巡检会重跑全部复现检查，起到回归测试的作用：已修复的问题如果复现检查再次失败，就产出回归信号。

- 用户在修复中给出的说明与决定(`--note`、`--reject --note`、`--accept-design`)记录在修复目录中，之后每次出计划与实施都交给全部修复角色，不需要重复说明。

**运行时验证**：修复阶段只做确定性检查、静态类与测试类复现检查和评审，不在本机启动后端做浏览器实测。运行时验证统一放到第 6 章，按固定的方式执行，避免同一条规则在不同运行中执行结果不一致。

## 5.7 输出

- worktree 中的未提交改动。
- 修复目录 `data/fixes/<Issue 编号>/` 中的交接文档(5.2)：结果文档 `result.md` 写明每项检查的结论与输出摘要、改动的文件与行数、任务外发现；`route.json` 记录通道、类型、档、处理标签与升级记录，`repro.json` 记录复现测试与基准结果；JSON 交接文档 `fix-<编号>.json` 供验证与发布读取，修复报告 `report.md` 由它渲染生成。
- Issue 回写 `branch` 字段，「历史」一节追加修复摘要：改了哪些文件、为什么这样改、检查与评审结果、遗留事项。

## 5.8 按风险分级评审

评审的深度由确定性的风险判定决定，不由模型判断。判定由核心的纯函数执行两次：出计划时对候选文件与分诊、计划的标记判定一次，在计划中标出风险；实施后对实际改动再判定一次，决定评审的深度。评审方式按通道：A 轻量(实际改动为微档且检查都通过时跳过)；B 轻量，高风险另加深度；C 不直接评审，各子 Issue 按 A 或 B。

**风险判定规则**：任一条命中即为高风险，否则为常规。

| 类别 | 按改动文件判定 | 按改动内容判定(新增与删除的行) | 按分诊与计划判定 |
|---|---|---|---|
| 数据库结构 | 路径匹配 `review.riskRules.schema.paths` | 匹配 `review.riskRules.schema.patterns` | 分诊或计划的「数据结构或存量数据」标记；计划的 `migration` 非空 |
| 权限与数据归属 | 路径匹配 `review.riskRules.authz.paths` | 匹配 `review.riskRules.authz.patterns` | Issue 的影响类别为权限或数据归属(3.5 的 P0 类) |
| 公共接口或契约 | 路径匹配 `review.riskRules.contract.paths`；改动落在 `authz-endpoints` 输出的端点处理方法所在文件中 | 匹配 `review.riskRules.contract.patterns` | 分诊或计划的「公共实现或接口契约」标记 |

规则的路径与模式是配置项，按 architecture/01 5.1 的四层配置合成：核心默认值为空；技术栈扩展给出通用的取值；项目只补充本项目特有的路径。各类别是否参与判定由 `review.deepTriggers.categories` 决定，默认三类都参与。

| 层 | `schema` | `authz` | `contract` |
|---|---|---|---|
| 技术栈扩展 `aspnetcore` | 路径 `**/Migrations/**`、`**/*DbContext.cs`；模式 `DbSet<`、`modelBuilder.` | 模式 `[Authorize`、`[AllowAnonymous` | 路径 `**/Controllers/**`；模式 `[Http`、`[Route` |
| 示例项目的 `project.yaml` | 路径 `src/Migrations/MigrationList.cs` | 路径 `**/PermissionMatrix.cs` | 无补充 |

**两种评审**

| 项 | 轻量评审 | 深度评审 |
|---|---|---|
| 适用 | A 通道；B 通道 | B 通道的高风险修复，与轻量评审一起运行 |
| 输入 | Issue 的结论、根因位置与验收标准；已确认的计划；相对基准 commit 的 diff；第 7 步的结果文档与疑似写死的字面量命中 | 同左，另加命中的风险类别、预取的同类缺陷模式 |
| 检查 | 5.2 的两类问题 | 5.2 的两类问题；另按命中的类别检查：权限与归属校验在所有入口生效、不只限制界面，受保护数据不因新查询外泄；数据结构变更可撤销、存量数据能被正确处理；契约变更的调用方与前后端字段一并改完 |
| 模型与预算 | 标准档，`stages.fix.review.light` | 强档，`stages.fix.review.deep`，须与 `fix-executor` 所用的工具或模型不同 |

## 5.9 参考

- Meta SapFix：自动生成补丁并通过测试后，交人工审批才发布；试点期从发现崩溃到提交人工审批的中位时间是 69 分钟。
- Google 的缺陷复现测试研究：先让 agent 生成能复现缺陷的测试，再交给自动修复系统，得到可行修复的缺陷数增加了 30%。
- LangChain 的自愈流水线：分诊确认后才交给编码 agent 修复并开 PR，合并前由人审阅。
- Anthropic 的提示词与 Claude Code 最佳实践：强模型容易过度设计，应在提示中明确只做要求的改动、不为假想需求增加抽象；评审被要求「找问题」时会报出与任务无关的问题，应限定只报影响正确性的问题；新模型不需要额外的「再验证一遍」步骤。
- Meta Diff Risk Score：按改动的风险打分，只标出约 10% 的改动即覆盖约 60% 的线上事故，据此把深度审查集中到高风险改动上。
- Google 的提交前测试：提交前只运行受改动影响的快速测试，全量测试放到提交后持续运行。
