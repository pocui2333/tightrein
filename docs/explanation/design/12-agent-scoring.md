# 12. 评分只作衡量

当前设计见 [redesign/08-learn.md](../redesign/08-learn.md) 第 2 节。

## 12.1 原则

- **评结果，不评过程**：看产出是否达标，不要求 agent 按某条固定路径完成。
- **能用代码评的用代码评**：构建、受影响的测试、复现检查、schema、证据位置、措辞、diff 规则、改动量由脚本判定，快、客观、可重复。
  质量主要靠这一层保证。
- **需要判断的只评审一次**：每个环节在确定性检查之后最多一次模型评审，不叠加多层评审，也不让生成者交付前再自查一遍。评审由另一个
  agent 执行，它没有写权限，看不到生成者的推理过程；只报告影响正确性或不满足需求的问题。分诊不设模型评审，修复的评审深度按 5.8 的
  风险判定决定。
- **不对模型做奖励或惩罚**：提示中不许诺奖励、不威胁惩罚(这类提示对有难度的任务没有稳定效果)；本工具调用现成模型，没有用奖励
  训练模型的通道。
- **分数不作为模型的目标**：提示中不告诉模型会按什么评分，评分也不只看测试通过率，防止模型为通过评分修改测试或针对测试数据写死
  特殊处理。分数给系统与用户看，不放进模型的提示。
- **人的决定是最终标准**：用户的改判、PR 的合并或关闭、撤销合并，用来校准前两种检查。

## 12.2 验收标准与评审项

每个产生 LLM 结果的环节都有一张条目表(`evaluation/rubrics/<环节>.json`)。生成者的提示中只出现条目文字，标题为「验收标准」，
让生成者动手前知道做到什么才算完成，不出现评分、分数与评分方式；评审者的提示中同样的条目带编号与判定方式，标题为「评审项」，
评审者对其中需要判断的项逐项给出结论。判定结果只给程序与用户。

**分诊**

| 条目 | 判定方式 |
|---|---|
| 每条证据都带 `文件路径:行号`，且文件与行号真实存在 | 代码 |
| 输出 JSON 字段齐全，判定属于四档之一 | 代码 |
| 判定为「不成立」时，现象来源指向真实存在的代码位置或主张中的某条事实 | 代码 |
| 做过反证检查：至少追到一个入口，每条写明入口位置与上游有无校验，位置真实存在 | 代码 |
| 结论不含「可能」「大概」「建议进一步排查」等含糊措辞 | 代码 |

**修复**

| 条目 | 判定方式 |
|---|---|
| 复现检查修复前失败、修复后通过 | 代码 |
| 项目检查(构建、受影响的测试、i18n)全部通过 | 代码 |
| 与本次改动相关的其他 Issue 的复现检查全部保持通过；这些检查不向修复 agent 展示 | 代码 |
| 改动量在 5.5 的上限内，改动文件都在计划中，没有触及未确认的受保护文件 | 代码 |
| 没有修改测试与复现检查，没有新增跳过测试的标记，没有调试残留与临时文件 | 代码(diff 规则与交付规则) |
| 没有针对复现输入写死的分支，没有为迁就测试而特判 | 代码初筛疑似写死的字面量，评审判定 |
| 改动满足 Issue 的验收标准，根因被修掉，没有破坏已有调用方 | 评审 |
| 高风险修复：命中类别的检查项(5.8)全部满足 | 深度评审；常规修复不适用 |

**提 Issue 与报告**：必需小节齐全、证据带位置、日期为绝对日期，由代码检查。

采集与归并是确定性脚本，不打分，用噪声占比等指标衡量(8.3)。

## 12.3 分数怎么起作用

1. **作为通过条件**：程序检查不通过的，把不满足的条目与实际结果交回生成者重做；仍不通过则交用户：Issue 转为待决定，问题进入
   人工队列。生成者看到的是「哪条验收标准没有满足、实际结果是什么」，不是分数。
2. **作为衡量**：一次通过率、修复是否真正有效、分诊准确率、用户纠正次数、每个修复的费用由程序统计(8.3)，写进周报，给系统与用户看。
3. **驱动系统层面的控制措施**，一律以建议进收件箱，凡改配置的都先交用户批准：
   - 某个模型的一次通过率连续 `thresholds.learn.controls.weeks` 周低于 `firstPassFloor`(每周样本不少于 `learn.minSamples`)时，
     建议写代码的调用点换用更强或其他模型，附对比评测的命令；
   - 用户一周内驳回修复计划、关闭 Issue 或撤销合并达到 `controls.corrections` 次，且对应关卡(`plan-confirm`、`issue-approve`、
     `merge`)为 `auto` 时，建议改为交用户确认；
   - 连续失败时停下转待决定，由编排的熔断完成(不改配置)。

原设计中用于排序的数值优先分不再使用(分诊改为决策树，13.2)。

## 12.4 防止投机

以分数为目标，agent 可能会走捷径让检查通过，而不是真正解决问题，例如写死值、针对复现输入特判、修改测试迁就实现。对策：

- 提示中不出现评分与分数；修复规则写明目标是把问题真正修好，而不是让检查通过；禁止写死值或针对测试特判，禁止修改测试迁就实现，
  发现测试本身不合理时报告而不是绕过。
- 评审专门检查是否只针对测试数据写了特殊处理；代码先初筛疑似写死的字面量交给评审。
- 修复 agent 看不到其他 Issue 的复现检查，这些检查作为隐藏回归测试。
- diff 规则由代码拦截：改动了测试、复现检查、验证脚本，或新增跳过测试的标记时直接判为不通过。
- 评分器、评测集、验证脚本不在任何 agent 的可写范围内(11.2)。
- 用真实结果交叉核对：检查通过而 PR 被关闭、或事后被撤销、回归的，作为条目表需要修订的证据。

## 12.5 评审的偏差与校准

- 模型评审已知有三种偏差：偏好某个位置的答案、偏好更长的答案、偏好自己生成的内容。评审不看生成者的推理过程，评审提示中要求不因
  篇幅加分；深度评审使用与 `fix-executor` 不同的工具或模型。
- 评审被要求「找问题」时，会报出与任务无关的问题。评审提示只要求报告 5.2 的两类问题，核心丢弃不带位置与触发条件的问题。
- 评审可以给出「无法判断」，此时交给人。
