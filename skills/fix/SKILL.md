# fix

修复由 `tightrein` 的子命令完成：分流、勘察、出计划、写复现测试、写代码、检查与评审都在子命令内部由各角色无人值守地执行，结果写入本工具的存储。本会话只负责按顺序调用子命令、把每一步的结果转述给用户、在需要时请用户明确表态。**不要自己编辑代码，不要执行任何 git 写操作。**

## 命令

```
tightrein fix plan <编号> [--note <要求>] [--accept-design]
tightrein fix confirm <编号> [--reject] [--note <说明>]
tightrein fix apply <编号> [--review-only]
tightrein fix done <编号>
tightrein fix abandon <编号> --reason <原因>
tightrein show <编号>
```

只读的 git 命令(`git status`、`git diff`、`git log`)可以用来向用户展示改动。每一步的进度写在 `data/fixes/<编号>/progress.md`，
各步的产出(计划、勘察结果、收集结果、评审意见、待决定事项)也在这个目录下，转述时可以引用。

## 通道

`fix plan` 先按分诊给出的任务类型与规模档查流程表(`fix.lanes`，项目可覆盖)：

| 通道 | 适用(缺省) | 经过的步骤 |
|---|---|---|
| A 快速 | 微档、小档，类型不是安全、数据、依赖 | Issue 即计划，自动确认；写复现测试、写代码、收集结果；轻量评审(微档且检查都通过时跳过) |
| B 标准 | 中档；或安全、数据、依赖类的任何规模 | 需要时勘察、出计划、确认计划；写复现测试、写代码、收集结果、轻量评审，高风险另加深度评审 |
| C 大任务 | 大档 | 出整体方案并拆成子任务，一律交用户确认；确认后其余子任务生成为排队的子 Issue |
| 超限 | 超过大档 | 不接：Issue 转待决定，`decision.md` 写明建议如何拆分需求 |

## 顺序

1. `fix plan`：分流(第 0 步)，A 通道直接给出计划并自动确认，转述后进入 `fix apply`；B、C 通道勘察(需要时)并出计划。
   - 用户的 `--note`、`fix confirm --reject --note` 与 `--accept-design` 会被记录下来，之后每次出计划与实施都交给全部修复角色，不需要重复说明；`--accept-design` 一经给出持续有效。
   - 「超出单个任务的上限」(`failed`)：转述 `decision.md` 的拆分建议，请用户拆分需求或 `fix abandon`。
   - 「修复通道调整」：计划的预估超出当前的档时只升不降，可能从 B 升为 C(需要拆分与用户确认)。
2. **计划确认**(B、C)：读 `data/fixes/<编号>/plan.md`，逐项向用户说明：
   - 改哪些文件、每一步改什么，预估改动量与规模档；计划带拆分时，说明本 Issue 只做第 1 个子任务，其余子任务确认后生成为排队的子 Issue；
   - 受保护文件的改动及理由、新增依赖、删除文件、数据结构变更与迁移条目(能否撤销、怎样撤销)；
   - 三类需要用户定夺的标记(根因在设计本身、数据结构或存量数据、公共实现或接口契约)与计划中列出的待定问题。
   关卡 `gates.plan-confirm` 为 auto 时，B 通道的计划按规则自动确认，输出写明「自动确认修复计划」时转述理由后直接进入 `fix apply`；C 通道的整体方案一律交用户。
   请用户明确表态，然后执行对应命令：同意为 `fix confirm <编号>`；要求调整为 `fix confirm <编号> --reject --note <要求>`；转为与代码作者讨论为 `fix abandon <编号> --reason <原因>`。没有明确表态时不要替用户确认。
3. `fix apply`：写复现测试(第 5 步)、写代码(第 6 步)、收集结果(第 7 步)、评审(第 8 步)与修改循环。转述结论：
   - `ok`：改了哪些文件、复现测试与检查结果、评审深度、未验证项与遗留事项。
   - 复现测试在未修改的代码上就通过：问题不成立，Issue 已退回分诊，告诉用户原因，会话结束。
   - 「写不出合格的复现测试」(`failed`)：请用户补充复现线索(触发的输入、期望的输出、可以放测试的位置)，然后执行 `fix start <编号> --here --force` 与 `fix apply <编号>`；或 `fix abandon`。项目没有配置 `testPaths` 或 `checks.commands` 时提示用户在 `project.yaml` 中配置。
   - 「转 B 通道」(`blocked`)：A 通道的实际改动超出当前的档，已写的复现测试保留，执行 `fix plan <编号>` 出计划。
   - `blocked` 的其他情况：说明原因与可选的处理命令。评审「无法判断」时请用户判断：视为通过用 `fix confirm <编号> --note <判断>`，要求重出计划用 `fix confirm <编号> --reject --note <要求>`；规范要求用户确认的事项(新增依赖、删除文件、未确认的受保护文件、边界违规)由用户用 `fix plan <编号> --note <决定>` 纳入新计划，或 `fix abandon`；项目检查命令无法运行时提示检查 `checks.prepare`。
   - `failed`：Issue 已转待决定(设计问题、修改或重出超过上限)，转述原因。
4. `fix done`：核对改动与 `apply` 结束时一致后进入合并前验证(复现测试随修复提交)，会话结束。`apply` 之后改动有变化时先执行 `fix apply <编号> --review-only`。

建修复分支后，本工具在基准版本上运行一次项目检查；不通过说明是配置或环境问题，Issue 转待决定(「项目检查在基准版本上不通过」)，请用户修正 `checks.commands`、`checks.prepare` 或环境后 `fix start <编号> --force`。

## 续接

会话中断后再次执行 `tightrein fix start <编号>`，本工具会从已完成的步骤之后继续，首条输入中写明当前停在哪一步；不确定时执行 `tightrein show <编号>` 或读 `progress.md`。
