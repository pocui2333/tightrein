# 修复规则

这份规则写给全部修复角色(勘察、出计划、写复现测试、写代码、评审)。修复的是其他开发人员写的代码，改动要让对方一眼看懂、愿意合并。

## 只修 Issue 描述的问题

- 修复的范围是 Issue 的「结论」「根因」「验收标准」描述的那个问题，不借机处理别的问题。
- 途中发现的其他缺陷、劣化代码与格式问题只写进输出的 `incidental`(任务外发现)，由本工具作为新问题登记，走正常的分诊流程。

## 最小修复

- 只做根治问题所需的最小改动，保持原有写法和结构。
- 不拆分文件，不抽取公共实现，不顺手重构、改名或调整格式。
- 不改公开接口与函数签名，除非计划中写明并说明理由。
- 不删除与本问题无关的代码，即使它看起来是死代码。
- 改动让附近注释描述的行为不再成立时，同步改写或删除这条注释；其余注释不动。
- 根因在设计本身、局部修补需要逐层加判断绕开、需要多处重复修补时，停下来说明，由用户决定是找代码作者讨论还是扩大修复范围，不硬凑一个局部补丁。

## 不过度设计

- 只做计划要求的改动。计划没写到的细节按项目现有惯例补齐，不自行增加功能。
- 只在系统边界做校验：接口入参、外部输入、外部服务的返回。内部调用之间不重复校验。
- 不为假想的需求增加抽象、参数、配置项或开关；不为「以后可能」预留扩展点。
- 测试只在写复现测试那一轮新建或追加，只覆盖 Issue 中观察到的真实行为；写代码时不新增、不修改测试。复现测试由本工具登记并随修复提交，修复不得改动它。

## 上限与受保护文件

- 当前规模档与单个 PR 的改动量上限(文件数与行数，不含测试文件)由任务给出。预估超出单 PR 上限时在计划中拆分；实际改动超出当前规模档时，本工具会转到更重的通道。
- 受保护文件清单由任务给出。计划要改动其中的文件、或增删受保护的内容时，必须在计划中逐项说明改什么、为什么，用户确认后才能改；未经确认的受保护文件一律不碰。
- 新增依赖、删除文件、数据结构变更同样要在计划中单列，由用户确认。

## 禁止投机

- 禁止写死值，禁止针对复现输入写特判分支。修复必须对同类输入都成立。
- 禁止修改测试、复现检查或验证脚本来迁就实现；禁止新增跳过测试、关闭告警、抑制类型检查的标记。发现测试本身不合理时，在输出中报告，不要绕过。
- 不伪造检查通过：检查没过就是没完成，如实写出。
- 不缩减需求：不得降级为简化版、只覆盖主流程而略过分支与边界、以占位实现或写死的返回值充当交付。做不到的部分如实说明。
- 不执行任何 git 写操作，不读取凭证与连接配置，不读取本工具的复现检查与评测目录。

## 完成标准

任务说明中附有验收标准，每一项都必须满足；能由程序判定的项(复现测试、全部项目检查、改动量与规模档、计划外文件、受保护文件、测试与跳过标记、调试残留)由本工具在写代码后执行，其余由独立评审基于这些实际结果判断。

动手前对照验收标准知道怎样算完成即可：不要求交付前再把检查全部跑一遍，也不要求用子 agent 复核。目标是把问题真正修好，而不是让检查通过。
