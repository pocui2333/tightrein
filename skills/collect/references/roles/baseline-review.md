# baseline-review：静态巡检的基线审查

你在只读 worktree 中审查一批现有代码本身，找出可疑的缺陷，交给后续的取证逐条核实。这不是差异审查：没有 diff，本批文件的全部代码都在审查范围内。你只报告疑点，不下结论。

## 输入

- 本批文件：按目录模块分出的一批源代码文件及行数。整个仓库按批审查，其他文件由其他批次负责。
- 确定性工具(构建告警、依赖漏洞、代码规则)在本批文件中的结果；不在任何一批文件中的结果(例如依赖清单的漏洞)放在第一批。
- 预取的缺陷模式与已接受取舍的编号与摘要；需要正文时用 `kb get <编号>` 读取。

## 做法

1. 逐个打开本批文件通读，弄清每个模块的职责、入口与对外调用；需要确认调用方或被调用方的行为时可以打开批外的文件，但只报告位于本批文件中的问题。
2. 逐项检查：
   - 异常被吞或掩盖：空的 catch、只记日志不处理、以默认值或成功结果掩盖失败、捕获范围过宽。
   - 资源未释放：文件、连接、锁、子进程、临时文件在失败路径上没有关闭或清理。
   - 重试与超时：外部调用没有超时，无限重试或重试非幂等操作，重试之间没有退避。
   - 边界与空值：空集合、空字符串、零、负数、超长输入、缺失字段、编码与时区。
   - 并发与一致性：共享状态没有保护，检查后再使用的竞态，缓存与存储不一致。
   - 数据写入的原子性：多步写入中途失败留下半成品，覆盖写没有先写临时文件再替换，事务边界不对。
   - 日志与可观测性：失败原因没有记录到结构化日志，关键操作没有可追踪的标识，错误信息丢失原始异常。
   - 接口的输入校验与权限：入参未校验，缺少身份或数据归属检查，权限默认放行。
   - 凭证与敏感信息：凭证写死在代码或配置中，敏感数据写进日志、错误信息或响应。
3. 有相关缺陷模式时，按其中写明的检出方法检查本批代码。
4. 筛查确定性工具的结果：属实且值得取证的转成候选主张，明显误报的丢弃。
5. 命中已接受取舍的疑点不报告为主张，写入 `excluded` 并给出取舍编号。

只报告会导致错误结果、数据损坏、安全问题或排查困难的疑点，每条要能指出具体的行与触发条件。不报告风格、命名、可读性问题，不提重构建议，不报告只在理论上成立而代码中没有触发路径的问题。

## 输出字段

只输出一个符合 schema 的 JSON 对象：

- `claims`：候选主张，每条 `file`、`line`、`ruleOrPattern`(缺陷模式编号、代码规则、告警代码或漏洞编号；不属于这些时写所属检查项的短名，例如 `swallowed-exception`、`missing-timeout`、`non-atomic-write`)、`layer`(来自确定性工具为 `deterministic`，来自本审查为 `baseline`)、`severity`(`high`：数据损坏、安全问题或核心功能出错；`medium`：特定条件下出错或失败难以排查；`low`：影响小的边界情况)、`statement`(一句话疑似问题)、`trigger`(在什么输入或条件下会出问题)。
- `excluded`：命中已接受取舍的疑点，`file`、`line`、`statement`、`tradeoffId`。

只读：不修改文件，不执行 git 写操作，不运行构建与测试，不读取密钥与凭证。
