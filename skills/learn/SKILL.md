# learn

learn 记录与衡量：读其他环节写下的数据库记录与交接文档做统计，写入范围只有指标快照、学习建议与决定文档、经验条目(经写入去重)、
工作区规则库 `rules/`、分诊结论与环节效益的回填、周报。它不执行复现检查、不判定回归，也不改任何配置、提示或代码：凡是改配置或提示的
调整都以建议进收件箱，`learn accept` 只记录用户的决定，由用户自己修改。

## 命令

```
tightrein learn report [--week <日期>] [--now <时间>]
tightrein learn metrics [--since <日期>] [--until <日期>] [--stage <模块>]
tightrein learn health
tightrein learn lessons
tightrein learn curate
tightrein learn improve [--days <天数>]
tightrein learn suggestions [--status <状态>] [--kind <类型>]
tightrein learn accept <建议编号> [--action renew|merge|archive]
tightrein learn reject <建议编号> --reason <原因>
```

| 想做什么 | 命令 |
|---|---|
| 生成或补生成某一周的周报 | `learn report --week <该周任一天>`；重跑同一周会覆盖该周的指标快照 |
| 只看指标，不写任何东西 | `learn metrics`，`--stage fix` 只看修复的一次通过率、费用等 |
| 检查链路是否正常 | `learn health` |
| 出问题时写经验、把修好的缺陷变成规则 | `learn lessons`(编排在每次运行结束时自动执行) |
| 经验清理与知识库复核 | `learn curate`(也包含在 `learn report` 中) |
| 从近期失败归纳一条改进建议并评测 | `learn improve`(只由用户运行：评测要多次运行模块，费用高；编排不触发) |
| 处理学习建议 | `learn suggestions --status pending`，再逐条 `accept` 或 `reject` |

所有命令支持通用参数；加 `--json` 时输出交接文档的 `outputs`，退出码 0 为完成，非 0 时读错误输出中的原因。

## 读周报

周报在 `data/reports/weekly-<周一日期>.md`，是 result 类型的交接文档：

| 小节 | 内容 |
|---|---|
| 结论 | 本周新发现、已修复、回归的数量与上周对比，修复一次通过率，需要处理的事项数、健康异常数与待处理的建议数；只读这一节就能判断本周要不要处理 |
| 做了什么 | 统计周期与生成时间 |
| 产出 | 指标表(本周、上周、趋势、样本数)、环节效益表、缺陷变规则的结果、经验清理、待处理的建议 |
| 证据 | 链路健康与第三方 skill 核实中的异常；逐项结果在数据块 `checks` |
| 偏离与原因 | 统计出错的项 |
| 需要决定 | 待处理的学习建议，每条带推荐与理由 |
| 下一步 | 需要处理的事项，每条带对象编号与命令 |

- **指标**：比率显示为百分比与分子分母；「无样本」表示分母为 0，「未知」表示分母缺失。修复的一次通过率按 `lane=`(通道)与
  `model=`(写代码的模型)分列，每个修复的费用与被撤销的比例按通道分列，用户纠正次数按类型分列。分数只作衡量，不放进任何模型的提示。
- **环节效益**：各 LLM 环节本周的调用数、token、费用，有效与无效产出数(只计结果已确定的调用，未定的单列)，每条有效产出的 token，
  以及最近一次有效产出之后又调用了多少次。某环节长期无有效产出，说明它可能可以删除或合并，这一判断由用户决定。
- **缺陷变规则**：本周处理的 Issue 各一行，收入规则库的给出 `rules/` 下的路径(之后静态巡检确定性地检测同类问题)，没有收录的写明
  原因(规则表达不了、修复前不命中、修复后仍命中、全仓库命中过多)，其缺陷模式描述已写进知识库。
- **下一步**的类别：

| 类别 | 处理 |
|---|---|
| Issue 等待放行 | 阅读 Issue 后 `tightrein approve <编号>` 或 `issue close` |
| PR 等待审核、PR 可以合并 | 打开给出的 PR 地址审核或合并 |
| 人工队列 | 补充信息后 `tightrein problem retriage <问题> --note <补充信息>`，或直接改判 |
| 抑制规则即将到期 | 编辑 `suppressions.yaml` 续期，或任其到期 |
| 自动判为误报(请抽查) | 抽查发现报告；判错时 `tightrein problem retriage <问题> --verdict confirmed --reason <原因>` |
| 回归两次及以上 | 局部修复没有根治，考虑设计层面的问题，重新评估 Issue |
| 待处理的建议 | 见下文 |
| 需要手写的经验 | 经验撰写多次失败，按给出的目录手写一条经验 |

## 经验与规则

- 经验只在出问题时写：分诊误判、PR 要求修改与修复评审不通过、修复转人工、撤销合并、用户驳回修复计划或关闭 Issue。正文末尾有
  「来源」一节，复核日期为写入日加设定天数。经验条目过了复核日期且长期没有被命中的自动归档，仍被命中的自动续期。
- 修好的缺陷由 `rule-writer` 写成 Semgrep 规则，程序用原补丁验证(修复前命中、修复后不命中、全仓库命中不超过上限)，通过的写进
  工作区 `rules/`。规则文件由程序维护，不要手改；误报多的规则可以直接删除该文件。

## 学习建议

| 类型 | 何时产生 | 接受后 |
|---|---|---|
| `probe-config` 采集配置 | 某检查的误报、被抑制、作废或间歇未复现的信号占比过高 | 只记录决定；按证据中的建议动作自己修改 `project.yaml` 的 `sources` 段 |
| `coverage-gap` 覆盖缺口 | 接口连续多周没有被覆盖 | 只记录决定；自己调整模糊测试范围 |
| `knowledge-review` 知识复核 | 缺陷模式、取舍等条目过期、长期未命中，或同类条目相互矛盾、重复 | 必须用 `--action`：`renew` 续期，`archive` 归档，`merge` 保留命中最多的一条、其余标为已取代 |
| `control` 控制措施 | 某模型的一次通过率连续多周偏低；用户一周内频繁纠正某类自动决定 | 只记录决定；按决定文档 `data/improve/<编号>.md` 的「下一步」自己修改配置(在 `routes` 中换别名，或把关卡改为 `user`) |
| `improvement` 改进建议 | 用户运行 `learn improve` 且评测完成 | 只记录决定；按决定文档自己应用：prompt 类在本工具仓库 `git apply` 同名 `.patch` 并提交，model 类在 `routes` 中改该调用点的别名 |

- **接受前必须向用户展示建议全文**(`learn suggestions` 的输出，含证据；控制措施与改进建议另展示决定文档，改进建议还要展示补丁与
  两组用例的评测对比)，得到用户同意后才执行 `learn accept`；不要替用户决定，也不要替用户应用补丁或修改配置。
- 改进建议的评测分为参与改进与未参与改进的用例；未参与改进的用例变差时推荐拒绝，用例不足时不会出建议。
- 拒绝时 `--reason` 写清楚为什么不采纳。同一对象被拒绝后，只有出现新的证据才会再次生成。
- 建议待处理超过设定周数会自动过期，周报不再列出。待处理的建议同时出现在收件箱中。

## 链路健康

`learn health` 的六项检查，出现异常时按这个顺序排查：

1. **异常退出**(立即通知)：看给出的事件日志与原始输出目录，先确认是工具失败还是环境问题。
2. **测试账号异常**(立即通知)：对应角色的测试账号无法登录，检查钥匙串中的凭证与账号状态。
3. **部署检测停滞**(立即通知)：有成功部署而没有部署后浅跑，检查定时任务是否在运行。
4. **漏跑**：列出错过的应执行时刻；最近连续漏跑时立即通知，常见原因是电脑休眠。
5. **长期没有产出**：连续多次运行都没有信号，结合给出的覆盖范围判断是否被拦在登录页等。
6. **数据目录膨胀**：按列出的子目录大小与保留期清理。

标为立即通知的项由编排合并进本次运行的通知，learn 自己只在周报生成后发一次通知。
