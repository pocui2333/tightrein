# 取证底线

分诊的全部价值在于结论可信。结论不可信时比不做更糟：会有人照着一个错误的判断去改代码。本文是所有分诊角色的取证底线，与任务说明中的验收标准逐项对应；这些标准都由程序检查，不满足的会被交回重做。交付即可，不需要自己再复核一遍。

## 通用底线

| 要求 | 为什么 |
|---|---|
| 每条事实带 `文件路径:行号` | 无法核对的结论等于没有结论；位置会被逐条核对是否真实存在、行号是否越界 |
| 路径写相对仓库根的完整路径，文字中引用代码也一样 | 只写文件名时本工具按代码快照补全，补不全(不存在或有多个同名文件)的交回重做 |
| 只写读到的，不写推测的 | 推测不是证据 |
| 打开文件读，不凭搜索匹配到的那一行下判断 | 匹配行看不到上下文，一个条件分支就能让结论反过来 |
| 同一概念试多种命名 | 只搜一个词就下结论必然会漏 |
| 数字要有来源 | 读不到就标「未确认」 |

### 「证据不足」是合格结论

写清缺什么信息、从哪里能补上(代码中可查，或只有用户知道)，就是合格的。**含糊其辞不是**：「可能」「大概」「也许」「似乎」「建议进一步排查」会被判为不合格。

## 缺陷类：怎样才算「成立」

四步走完才能判定：找到相关代码 → 读懂实际逻辑 → 找触发条件 → 找反证。

### 反证要追到入口

很多保护在调用链上游。只看出事的函数，会把有保护的代码误判为缺陷。沿调用链往上追到入口(路由、控制器、页面事件)，逐层看：鉴权声明、参数校验、归属过滤、数据库约束与事务。

- 每条反证检查写明追到的入口(`文件路径:行号`，或原样引用主张中的入口)，以及上游有没有校验；有校验时给出校验的位置。
- **前端拦截不算反证**：前端挡住而接口没挡，恰恰是一条缺陷。

### 判「不成立」的要求

必须指出挡住它的那段代码(`文件路径:行号`)，或者引用主张中的某条事实说明现象的真实来源(例如请求本身不合法)。只说「没问题」不合格。

## 响应偏慢：怎样才算「算过了」

- 必须是算式，不是形容词：「40 人 × 每 5 秒 1 次 = 8 次/秒，每次 41 条查询 = 328 次/秒到库」。
- 稳态与峰值分开算，两者的瓶颈往往不是同一环。
- 瓶颈指名道姓：哪一环(`文件路径:行号`)、在多大负载下到顶。
- 静态推算就说是推算，并写明怎样实测。

## 评估：怎样才算「估过了」

- 改动文件数用搜索数出来，列出清单(不含测试文件)；已有文件必须真实存在，新建的标明；行数按要改的代码估，不按整个文件。
- 逐一确认：是否触及公共实现或接口契约、是否要改数据结构或存量数据、前后端是否要配对修改、有无测试兜底。
- 不修的代价要具体：谁、多久撞一次、多糟、能否绕开、会否恶化。
- 同一根因的多个现象只算一份代价。
- 安全、权限、数据正确性三类不按性价比判为暂不修或不该修。

## 反模式清单

| 反模式 | 问题 |
|---|---|
| 结论没有行号 | 无法核对 |
| 「可能」「大概」「建议进一步排查」 | 把问题原样推回去 |
| 响应偏慢的结论没有算式 | 感觉不是证据 |
| 判「不成立」但没说现象从哪来 | 等于没查 |
| 数字来源是「一般来说」「通常」 | 假数字比没数字危险 |
| 把主张的措辞当成已确认的事实 | 主张不是结论 |
| 只看出事的函数，没往上追入口 | 会把有保护的代码误判为缺陷 |
| 前端挡住了就判不成立 | 接口没挡的话，这恰恰是缺陷 |
| 建议优化但没说省多少 | 无法判断值不值得 |
| 顺带给出与本问题无关的改进建议 | 超出任务范围，干扰判断 |
