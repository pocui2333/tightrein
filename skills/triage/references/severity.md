# 严重度标准与 Issue 报告

判定为成立(`confirmed`、`conditional`)时，输出 `report`，供本工具生成 Issue；判定为不成立或证据不足时 `report` 为 null。`report` 是写给项目维护者读的，不是写给本工具的。

## 严重度

按「不修会怎样」定级，不按问题类别套用；同一类别在不同项目、不同范围下可以是不同的级别。

| 级别 | 含义 | 例子 |
|---|---|---|
| `P0` | 线上不可用、数据丢失或泄露、安全漏洞(可被利用的越权、凭证泄露、注入) | 登录后可读写他人数据；保存时静默丢弃用户数据；主流程整体不可用 |
| `P1` | 核心功能错误，或数据长期错误但有替代办法 | 核心报表的数字持续算错，但可以人工核对；主流程某一步失败需绕路 |
| `P2` | 非核心功能错误，或偶发(特定时序、少见输入才出现) | 次要页面报错；极少数输入导致一条记录格式不对 |
| `P3` | 轻微：体验、规范、慢但能用、可忽略的边界情况 | 文案、提示不清；无害的冗余请求 |

- 先看范围：影响多少用户、多少数据、多久撞一次；只影响个人或本机、能事后修复的数据问题一般不到 P0。
- 再看能否绕开与是否恶化：有替代办法的降一级；脏数据持续累积、无法事后修复的升一级。
- `severityReason` 一句话写清依据(影响范围、能否绕开、会否恶化)，不写类别名代替理由。
- 下文的「项目说明」(如有)给出本项目的语境，与本表冲突时以项目说明为准。

## report 字段

- `title`：「[模块] 一句话说清现象与后果」。模块取顶层目录或功能名(如 `[utils/monitor]`、`[导出]`)；不写规则名、文件路径与符号；不超过任务给出的字符上限。
- `summary`：问题本身，一两句：什么情况下、出了什么错、导致什么后果。
- `steps`：触发条件或复现步骤，每步一条，按顺序；静态问题写出走到这段代码所需的输入与操作。
- `expected`、`actual`：期望的行为与实际的行为；说不清时为 null。
- `acceptance`：修好的判定条件，每条可以验证(运行哪个命令、调用哪个接口、看到什么结果)，至少一条；不写「代码更清晰」这类无法验证的条件。
- `severity`、`severityReason`：按上表。

代码位置一律写相对仓库根的完整路径(`processors/rule_extractor.py:177`)，正文文字中引用代码时同样如此，不只写文件名。
